## 背景：为什么是 FlashInfer

FlashInfer 被 vLLM、SGLang、TensorRT-LLM 等主流 serving 框架使用，并且在持续加入新模型需要的算子：MLA、GDN / KDA 等线性 attention、NVFP4 / MXFP8 GEMM 和 MoE、DiT 的融合 norm、sm_110 / sm_120 的专用 kernel。它的代码同时包含 CUDA C++（`include/`）、CuTe DSL（`flashinfer/cute_dsl`）、Triton（`flashinfer/triton`），以及对 cuDNN、TRT-LLM、CUTLASS 后端的封装，所以对想做 kernel 工作的人来说，它几乎覆盖了整个技术栈。

本页的内容都核对过 FlashInfer 主分支 2026-11-02 的源码和它自带的 `CONTRIBUTING.md` / `CLAUDE.md`。项目变化很快，动手前以仓库里的最新版本为准。

## 源码地图

| 目录 | 放什么 | 规则 |
|---|---|---|
| `include/flashinfer/` | kernel 定义（`.cuh`）：只接收裸指针，与框架无关 | **不能 include Torch 头文件** |
| `csrc/` | launcher 和绑定：把张量转成指针、选模板实例、调用 kernel | TVM-FFI 绑定在 `*_jit_binding.cu` / `*_binding.cu` |
| `flashinfer/jit/` | JIT 模块生成器：列出要编译的源文件和 nvcc 参数 | 例如 `jit/norm.py` 的 `gen_norm_module()` |
| `flashinfer/*.py`、`flashinfer/<模块>/` | Python API：参数检查、选择后端、`@functools.cache` 缓存编译好的模块 | 公开 API 用 `@flashinfer_api` 装饰 |
| `flashinfer/triton/`、`flashinfer/cute_dsl/` | Triton 和 CuTe DSL 写的 kernel | 其中有 `norm.py`、`activation.py`、`cascade.py`，正好对应 F2、F3 |
| `flashinfer/experimental/` | 实验性后端（比如 SM12x 消费级 GPU 的 kernel） | 需要 owner 和 tracking issue |
| `tests/<领域>/`、`benchmarks/` | pytest 测试；`flashinfer_benchmark.py` 统一 benchmark | 按 GPU 架构跳过用 `flashinfer.utils` 中的检测函数 |

**JIT 是怎么工作的**：第一次调用某个 API 时，FlashInfer 按 dtype、head_dim 等参数生成专门的 CUDA 代码，用 ninja 编译，把 `.so` 缓存到 `~/.cache/flashinfer/`；之后的调用直接加载。修改 `.cuh` 后不需要手动重新构建，再次运行时它会检测到变化并重新编译。

## Lab 1：开发环境

在 GPU 机器上执行（本仓库的 `setup_env.sh` 已经准备好 nvcc；FlashInfer 本身需要 CUDA 12.x 或 13.x 的 toolkit）：

```bash
git clone --recursive https://github.com/flashinfer-ai/flashinfer.git && cd flashinfer
python -m pip install --upgrade pip setuptools
pip install --no-build-isolation -e . -v        # --no-build-isolation：用你环境里已有的 torch
pip install pre-commit && pre-commit install
python -m flashinfer.collect_env                # 报 bug 时附上这份环境信息
```

`--no-build-isolation` 很重要：不加的话，pip 可能另外下载一个用不同 CUDA 版本构建的 torch。

## Lab 2：沿一个算子追到底（RMSNorm）

1. `flashinfer/norm/__init__.py` 中的 `rmsnorm()`：参数检查，然后调用 `get_norm_module().rmsnorm(out, input, weight, eps, enable_pdl)`。
2. `get_norm_module()` → `flashinfer/jit/norm.py` 的 `gen_norm_module()`：列出 `csrc/norm.cu` 和 `csrc/flashinfer_norm_binding.cu`，加上 `-DENABLE_BF16 -DENABLE_FP8`。
3. `csrc/norm.cu`：把张量转成指针，按 dtype 分发，调用 `flashinfer::norm::RMSNorm<T>(...)`。
4. `include/flashinfer/norm.cuh` 中的 `RMSNorm`：`vec_size = gcd(16 / sizeof(T), d)`，每行一个 block，`cudaLaunchKernelEx` 加上 PDL 属性。kernel 本体是 `RMSNormKernel`：向量化加载、warp 归约、shared memory 汇总。把它和你的 T3、F3 对照着读。

动手：

```bash
export FLASHINFER_JIT_VERBOSE=1
pytest tests/norm -k "rmsnorm and not cake" -x -q    # 第一次运行会看到 JIT 编译日志
# 在 RMSNormKernel 里随便改一处（比如加一行注释），再运行一次：会看到它重新编译
```

## Lab 3：用官方工具做 benchmark

```bash
pip install -U cupti-python        # CUPTI 计时，比 CUDA event 更准；没有时自动回退
python benchmarks/flashinfer_benchmark.py \
    --routine BatchDecodeWithPagedKVCacheWrapper --backends fa2 \
    --batch_size 32 --s_kv 2048 --num_qo_heads 32 --num_kv_heads 8 \
    --head_dim_qk 128 --head_dim_vo 128 --page_size 16 --refcheck -vv
```

- 在 RTX 5090 上只能使用 `fa2` 等通用后端；`trtllm-gen`、`cutlass` 的部分后端需要 sm_100。先看清楚哪些后端支持你的 GPU。
- 写 benchmark 代码时用 `flashinfer.testing.bench_gpu_time`（返回每次迭代的耗时列表，取中位数）。
- 把这里的数字和你的 F1 / L3 对照。

## Lab 4：选一个贡献方向

按入门难度由低到高：

| 方向 | 例子 | 你在本套题里已有的准备 |
|---|---|---|
| **文档与示例** | 补全 docstring 中缺少的形状 / dtype 说明；写一个 CSR 分页格式的示例 | F1 |
| **测试** | 给某个 API 加上边界情况（非 2 的幂的 head_dim、空序列、非连续输入）；补全 sm_120 上的测试覆盖 | 所有题的测试写法 |
| **benchmark** | 给某个还没有 benchmark 的 API 写 routine，比较不同后端 | 每题的“测完之后” |
| **消费级 GPU 支持** | 找出在 RTX 5090（sm_120）上不能运行或运行很慢的 API，按 experimental 规范补一个后端 | 你有 5090；L、F、M 系列 |
| **Triton 实现** | `flashinfer/triton/` 中算子的性能或功能改进（如 merge_state 的向量化） | T 系列、F2、F3 |
| **新算子** | 新模型需要的融合算子（新的 norm 变体、量化格式、attention 变体） | 全部 |

寻找切入点：在 GitHub issues 中搜索与你的硬件或熟悉的算子有关的内容；读 `docs/design_docs/`；跑一遍 `pytest tests/<你关心的目录>`，看看在你的 GPU 上哪些测试被跳过、哪些失败。

## 新算子的标准流程（来自项目的 CLAUDE.md）

1. 在 `include/flashinfer/new_op.cuh` 中写 kernel（框架无关，只用裸指针）。
2. 在 `csrc/new_op.cu` 中写 launcher（处理 PyTorch 张量）。
3. 在 `csrc/new_op_jit_binding.cu` 中写 TVM-FFI 绑定。
4. （可选）需要按类型特化时，写 Jinja 模板。
5. 在 `flashinfer/jit/new_op.py` 中写 JIT 模块生成器。
6. 在 `flashinfer/new_op.py` 中写 Python API，用 `@functools.cache` 缓存模块。
7. 在 `tests/` 中写测试。
8. 在 `flashinfer/aot.py` 中注册 AOT 编译。
9. 在 `flashinfer/__init__.py` 中导出。
10. 在 `flashinfer/trace/templates/` 中加 `TraceTemplate`，用 `@flashinfer_api(trace=...)` 接上。
11. 在 `tests/trace/example.py` 中加调用示例，重新生成并提交 `fi_trace_out/` 下的 JSON。

官方推荐的参考实现：简单的看 `flashinfer/norm/__init__.py`（RMSNorm，不用 Jinja），中等的看 `flashinfer/sampling.py`（用了 Jinja），复杂的看 `flashinfer/decode.py`（plan / run 模式，workspace 管理）。

## PR 规范（最常被忽略的几条）

- **保留默认的 PR 模板**（`.github/pull_request_template.md`）：Description、Related Issues、Checklist、Tests、Reviewer Notes。不要换成自己的格式：squash merge 之后，标题和描述就是 commit message。
- **性能 PR 必须给出改动前后的绝对数字**：用可复现的 benchmark（比如 `flashinfer_benchmark.py`），写明 GPU 型号和问题规模。只给加速比、或者不说 GPU 型号，都不够。
- **提交前运行** `pre-commit run -a`。
- **CI 默认只跑相关的测试**：在 PR 中评论 `@flashinfer-bot run tests/<目录或文件>`，只写与改动有关的路径；不带路径会跑全部测试，代价很高。
- **experimental 规范**：消费级 GPU（SM12x）的 kernel、针对最新模型的新算子，走 experimental 路线：后端放在 `flashinfer/experimental/`，API 用 `@flashinfer_experimental_api` 标记，需要一个写明 owner、原因和转正计划的 tracking issue。`backend="auto"` 只有在设置 `FLASHINFER_ALLOW_EXPERIMENTAL_AUTO_BACKENDS=1` 时才会选到实验性后端。

::: answer 面试追问：FlashInfer 为什么用 JIT，而不是把所有 kernel 预先编译好？
attention 这类 kernel 的模板参数组合非常多：dtype（q、kv、o 各自不同）× head_dim × 位置编码 × 是否滑动窗口 × 是否 soft cap × 架构（sm_80 / 90 / 100 / 120）……全部预编译，wheel 会非常大，编译时间也难以接受，而大部分组合没有人用。JIT 只编译实际用到的组合并缓存，新架构、新变体也可以很快加入。对部署来说，可以用 AOT（`flashinfer/aot.py`）或预编译的 cubin / JIT cache 包，提前把需要的组合编译好，避免线上第一次调用时卡几十秒。
:::
