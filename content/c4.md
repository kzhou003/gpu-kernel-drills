lede: GEMM 是 GPU 性能工程的母题：每一级优化都在做同一件事，提高“每从慢存储读一个数，能做多少次乘加”。

## 背景

Transformer 里绝大部分 FLOPs 都在矩阵乘：QKV 投影、MLP、LM head。计算 `C[M,N] = A[M,K] @ B[K,N]` 需要 `2MNK` FLOPs，而 A、B、C 一共只有 `MK + KN + MN` 个数。n = 4096 时，每个数平均被用了约 2700 次。**算法本身的复用度极高，问题是 naive 实现完全没利用这一点。**

| 版本 | 每次 FMA 需要的 global 读 | 关键思想 |
|---|---|---|
| v0 naive | 2 次（各读 A、B 一个数） | 无复用，memory-bound |
| v1 shared memory tiling | 2 / 32 | 32×32 的 tile 读进 shared memory，每个数在 block 内被复用 32 次 |
| v2 register tiling | 再减少 shared memory 读取 | 每个线程算 4×4 个输出：从 shared memory 读 4+4 个数，做 16 次 FMA |
| v3 Tensor Core（扩展） | | `mma` 指令一次算一个小矩阵块；Triton 的 `tl.dot` 自动使用（T4） |

## 要用到的知识

- **二维 tile 的协作加载**：block 内每个线程搬一部分，`__syncthreads()` 之后所有人都能用整块。
- **越界填 0**：超出矩阵的部分装 0，对点积没有贡献，内层循环就不需要边界判断。
- **load → sync → compute → sync**：第二个 sync 防止下一轮的 load 覆盖还在被读的 tile。
- **寄存器数组**：`float acc[TM][TN]`。循环边界是编译期常量并且 `#pragma unroll` 时，数组会完全放进寄存器。
- **外积**（outer product）：`acc[i][j] += a[i] * b[j]`，读 TM + TN 个数，做 TM·TN 次 FMA。
- `__launch_bounds__(THREADS)`：告诉编译器 block 大小，便于分配寄存器。

## 提示

::: hint 1 先只做 smem 版
- 内层先只想“一个 tile 步”：A 的 tile 是 `A[by·32 : +32, k0 : +32]`，B 的 tile 是 `B[k0 : +32, bx·32 : +32]`。
- 线程 (ty, tx) 正好装 A tile 的 `[ty][tx]` 和 B tile 的 `[ty][tx]`。
- 输出 `C[row][col] += Σ_k As[ty][k] · Bs[k][tx]`。
:::

::: hint 2 regtile 的线程分工
- 256 个线程排成 16×16：`tx = tid % 16` 管第 tx 组 4 列，`ty = tid / 16` 管第 ty 组 4 行。
- **加载**：A 的 tile 有 64×16 = 1024 个数，256 个线程每人搬 4 个：`for (e = tid; e < BM*BK; e += THREADS)`，`m = e / BK, k = e % BK`，存成 `As[k][m]`。B 的 tile 有 16×64 个数，`k = e / BN, n = e % BN`，存成 `Bs[k][n]`。e 连续时 k（或 n）连续，所以 global 读是合并的。
- **计算**：对每个 k，`a_frag[i] = As[k][ty*4 + i]`，`b_frag[j] = Bs[k][tx*4 + j]`，然后做 4×4 外积。
- **为什么 A 要转置存**：这样 `a_frag` 读的是 `As[k][...]` 里连续的 4 个数，而不是跨行跳着读。
:::

::: hint 3 regtile 内层
```cpp
for (int k = 0; k < BK; ++k) {
  for (int i = 0; i < TM; ++i) a_frag[i] = As[k][ty * TM + i];
  for (int j = 0; j < TN; ++j) b_frag[j] = Bs[k][tx * TN + j];
  for (int i = 0; i < TM; ++i)
    for (int j = 0; j < TN; ++j) acc[i][j] += a_frag[i] * b_frag[j];
}
// 写回：gm = block_row + ty*TM + i, gn = block_col + tx*TN + j，越界跳过
```
:::

## 测完之后

RTX 5090 实测（FP32，关闭 TF32，单位 TFLOP/s）：

| n | naive | smem | regtile | cuBLAS |
|---|---|---|---|---|
| 512 | 5.2 | 5.2 | **2.5** | 16.3 |
| 2048 | 7.4 | 8.7 | 22.1 | 63.3 |
| 4096 | 7.4 | 9.1 | **33.0** | 65.4 |

- 大矩阵时 register tiling 比 smem 快 3.6 倍，达到 cuBLAS 的一半。
- **smem 只比 naive 快一点**：5090 的 L1 / L2 很大，naive 的大量重复读取其实命中了 cache。shared memory tiling 在 L2 较小的老 GPU 上收益更明显，register tiling 才是这里真正的提升。
- **512 时 regtile 反而最慢**：64×64 的 tile 只切出 64 个 block，5090 有 170 个 SM，大部分 SM 都闲着。这就是下面面试追问里说的 wave quantization / SM 利用率问题。

- 用 `ncu` 看 regtile 的**寄存器数**和 occupancy：TM、TN 改成 8 会怎样？更多复用，但寄存器压力更大，可能溢出到 local memory（`ncu` 里叫 `spilling`）。
- `As[k][m]` 的写入有 bank conflict（m 方向跨 64）。可以改成 `float4` 向量化加载，或给 As 加 padding，看看能提升多少。
- **双缓冲**：用两组 shared memory tile，计算当前 tile 时预取下一个 tile。这就是 Triton 里 `num_stages` 做的事。
- **Tensor Core**：用 `nvcuda::wmma`（`#include <mma.h>`）把 16×16×16 的 half 精度块交给硬件，FP16 下可以再快一个数量级。T4 里的 `tl.dot` 会自动用上 Tensor Core。

::: answer 面试追问：tile 越大越好吗？
不是。tile 越大，每个数的复用度越高（算术强度 ∝ tile 边长），但一个 block 占用的 shared memory 和寄存器也越多，每个 SM 能驻留的 block 和 warp 就越少，访存延迟更难隐藏。矩阵本身较小时，大 tile 还会导致 block 数不足，喂不满所有 SM（wave quantization）。所以实际做法是对每个 shape 做 autotune，T4 就是这么做的。
:::
