## 背景

和 C1 一样，这是一个 memory-bound 的融合 kernel：`gelu(x + y)`（残差加 + 激活）。它在这里的意义是**熟悉 Triton 的基本动作**：program_id、arange、mask、load、store、dtype 转换、grid。后面每一道 Triton 题都建立在这几个动作上。

## 要用到的知识

- `pid = tl.program_id(axis=0)`：当前 program 的编号（对应 CUDA 的 blockIdx）。
- `offs = pid * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)`：这个 program 负责的 BLOCK_SIZE 个下标（一个向量）。
- `mask = offs < n_elements`，`tl.load(ptr + offs, mask=mask, other=0.0)`，`tl.store(ptr + offs, val, mask=mask)`。
- `.to(tl.float32)` 和 `out_ptr.dtype.element_ty`：fp16 输入时先升到 fp32 计算，存回时转回原类型。
- `tl.sigmoid`；`tanh(u) = 2·sigmoid(2u) − 1`。
- launch：`kernel[grid](args..., BLOCK_SIZE=1024)`，`grid = (triton.cdiv(n, BLOCK_SIZE),)`。

## 提示

::: hint 1 结构
这个 kernel 只有 5 步：算 offs → 算 mask → 两次 load（转 fp32）→ 计算 → store（转回输出类型）。wrapper 也是：`contiguous()` → `empty_like` → grid → launch。
:::

::: hint 2 常见坑
- 忘了 `mask`：最后一个 program 会读写越界。解释器模式下可能直接报错，GPU 上可能悄悄写坏别的内存。
- 没有转 fp32：fp16 下 `z³` 在 |z| > 40 左右就会溢出成 inf。
- 存储时没转回：fp32 的值写进 fp16 指针会报类型错误，或者在某些版本上被隐式截断。
- 非连续输入：kernel 把指针当扁平数组用，`x.t()` 这类 view 直接传进去会读错位置，所以 wrapper 里要先 `.contiguous()`。
:::

::: hint 3 kernel 主体
```python
pid = tl.program_id(axis=0)
offs = pid * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
mask = offs < n_elements
x = tl.load(x_ptr + offs, mask=mask, other=0.0).to(tl.float32)
y = tl.load(y_ptr + offs, mask=mask, other=0.0).to(tl.float32)
z = x + y
t = 2.0 * tl.sigmoid(2.0 * 0.7978845608028654 * (z + 0.044715 * z * z * z)) - 1.0
tl.store(out_ptr + offs, (0.5 * z * (1.0 + t)).to(out_ptr.dtype.element_ty), mask=mask)
```
:::

## 测完之后

- RTX 5090 实测（fp16，n = 2²⁶）：PyTorch 两个 kernel 434 us · 927 GB/s，参考解 **260 us · 1548 GB/s**。和 C1 的 CUDA 版一样到了带宽上限：编译器自动做了向量化，每个线程一次读 16 字节（fp16 就是 8 个元素）。
- 试试 `block_size` 取 128、256、…、8192，以及 `num_warps=2/4/8`，结果有什么变化？
- 看编译产物：`k = add_gelu_kernel[grid](...)`，然后 `print(k.asm["ttgir"])`，找到 `#blocked = #ttg.blocked<{sizePerThread = [...], threadsPerWarp = [32], warpsPerCTA = [...]}>`。这就是 G1 要讲的 layout。

::: answer 面试追问：Triton 的 program 和 CUDA 的 block 是什么关系？
一个 program 在 GPU 上就是一个 CUDA block（CTA），由 `num_warps × 32` 个线程组成。你写的块级操作（比如长度为 BLOCK 的向量加法）会被编译器按 layout 拆给这些线程，每个线程负责若干个连续元素。因此 Triton 里没有 threadIdx：线程这一层由编译器管理，你管理的是 program 这一层的数据分块。
:::
