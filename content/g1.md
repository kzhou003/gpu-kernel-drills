lede: Triton 替你决定、Gluon 让你自己决定的那件事：一个块级张量的每个元素到底在哪个 warp、哪个 lane、哪个寄存器里。用纯 Python 把它算出来。

## 背景

Triton 代码里，一个 `[64, 64]` 的张量看起来像一个整体；但在硬件上，它被拆给 4 个 warp × 32 个 lane，每个线程持有若干寄存器。这种拆法叫 **layout**，它决定了：

- 一次 load 能不能向量化、是否合并访存；
- `tl.sum(x, axis=1)` 是在线程内完成、需要 warp shuffle，还是需要经过 shared memory；
- 两个张量 layout 不同时，必须做一次 layout 转换（通常要经过 shared memory，很贵）。

原计划 Week 6–7 的 Gluon 学习检查点，第一条就是“能解释一个 tensor 的元素如何映射到不同线程”。这道题把这件事变成可以测试的代码，不需要 GPU，也不依赖某个 Gluon 版本的 API。

## 要用到的知识：BlockedLayout

```text
BlockedLayout(size_per_thread  = [1, 4],   # 每个线程拿 1 行 × 4 列连续元素（一个 chunk）
              threads_per_warp = [4, 8],   # 一个 warp 的 32 个 lane 排成 4 × 8
              warps_per_cta    = [4, 1],   # 4 个 warp 沿行方向叠起来
              order            = [1, 0])   # 编号时维度 1（列）变化最快
```

一个 CTA tile 覆盖 `tile[d] = spt[d] · tpw[d] · wpc[d]` 个元素：这里是 `[1·4·4, 4·8·1] = [16, 32]`。

**线程 (warp, lane) 的第 s 个 chunk 元素、第 rep 次重复，对应的坐标：**

```text
lane_c = 按 order 把 lane 拆成各维坐标（threads_per_warp 为各维大小）
warp_c = 按 order 把 warp 拆成各维坐标（warps_per_cta 为各维大小）
coord[d] = rep[d] · tile[d] + warp_c[d] · (spt[d] · tpw[d]) + lane_c[d] · spt[d] + s[d]
coord[d] %= shape[d]          # 张量比 tile 小时取模：多个线程持有同一元素（broadcast）
```

- 张量比 tile **大**：tile 沿该维重复 `shape[d] / tile[d]` 次，每个线程多出相应倍数的寄存器。
- **寄存器编号**（本题约定，和 Triton 的编号方式一致）：先编一个 chunk 内的元素，再编重复次数，两者都按 `order` 线性化。
- “按 order 拆分”：`order[0]` 是最快变化的维度。比如 `tpw = [4, 8]`、`order = [1, 0]` 时，lane 9 → 维度 1 取 `9 % 8 = 1`，维度 0 取 `9 // 8 = 1`，即 lane 坐标 (1, 1)。

**例子**（shape `[16, 32]`）：warp 0 lane 0 持有 `(0,0) (0,1) (0,2) (0,3)`；lane 1 持有 `(0,4)…(0,7)`；lane 8 持有 `(1,0)…(1,3)`；warp 1 lane 0 持有 `(4,0)…(4,3)`。

## 要用到的知识：SliceLayout、归约与合并访存

- **SliceLayout(dim, parent)**：从 parent 中去掉 dim 这一维得到的一维 layout，`tl.sum(x, axis=dim)` 的结果就是这种 layout。线程持有的是它在 parent 中元素坐标去掉 dim 之后的值（去重）。例如沿 axis=1 求和后，warp 0 的 lane 0–7 都持有第 0 行的和：同一个值复制了 8 份。
- **归约的代价**沿 `axis` 分三层：线程内 `spt[axis] · reps[axis]` 个值先相加；然后在 lane 之间做 `log2(tpw[axis])` 轮 butterfly shuffle；如果 `wpc[axis] > 1`，还要把各 warp 的部分和经过 shared memory 和一次 barrier 汇合，这一步最贵。
- **合并访存**：一个线程一条指令最多读 16 字节，即 `vec = min(spt[order[0]], 16 / dtype_bytes)` 个元素。数一下一个 warp 的第一条 load 用到了多少个 32 字节 sector：理想情况下 `sector 数 × 32 = 请求的字节数`。

::: callout analogy 发扑克牌
先把牌桌分成几个区（warpsPerCTA），每个区里按座位（threadsPerWarp）发牌，每人一次拿几张连号的牌（sizePerThread）；`order` 决定是先横着发还是先竖着发。
连号的牌正好是内存里相邻的地址时，一个人一次就能拿起一整摞（向量化），一桌人拿的牌也挨在一起（合并访存）。

## 提示

::: hint 1 先写 _delinearize
`for d in order: coords[d] = index % sizes[d]; index //= sizes[d]`。lane 坐标、warp 坐标、chunk 内坐标、重复坐标全都用它。
:::

::: hint 2 thread_elements 的两层循环
外层循环重复次数 `rep_i in range(prod(reps))`，内层循环 chunk 内元素 `s_i in range(prod(spt))`，各自用 `_delinearize` 拆成坐标，然后套用坐标公式并对 shape 取模。这个循环顺序就是寄存器编号的顺序。
:::

::: hint 3 其余函数都是 thread_elements 的组合
- `owners`：枚举所有 `(warp, lane)` 和寄存器，比较坐标。
- `slice_elements`：`rest = c[:dim] + c[dim+1:]`，用 set 去重。
- `reduce_plan`：直接套公式（`int(log2(tpw[axis]))`）。
- `warp_load_sectors`：对 32 个 lane 取 `thread_elements(...)[:vec]`，地址 = `Σ coord[d] · stride[d] · bytes`，行主序 `stride[d] = prod(shape[d+1:])`，sector 编号是 `addr // 32`，统计集合大小。
:::

k = softmax_kernel[(M,)](y, x, x.stride(0), y.stride(0), N, BLOCK_SIZE=1024, num_warps=4)

把编译器选的参数代进你的 `reduce_plan`：`tl.max` 和 `tl.sum` 是否需要跨 warp？`num_warps` 改成 1 呢？再看 T4 的 GEMM：`#mma`（Tensor Core 的累加器 layout）、`#dot_op`、`#shared` 这几种 layout 分别出现在哪，它们之间的 `ttg.convert_layout` 就是编译器替你安排的数据搬运。

::: answer 面试追问：为什么 `order` 对行主序张量很重要？
`order[0]` 决定哪一维在 lane 和寄存器编号中变化最快。行主序张量里列方向在内存中连续，所以 `order = [1, 0]` 时，一个线程的 chunk 和相邻的 lane 都落在连续地址上，可以向量化、也能合并访存。反过来用 `[0, 1]`，一个线程的“连续”寄存器会落在不同的行上，同样的数据需要更多 sector（测试里的 BAD layout 正好浪费一半带宽）。
:::
