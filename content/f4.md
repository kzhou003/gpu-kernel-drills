lede: 15 万词表上的 top-k / top-p：不排序，只做若干次全词表的归约来逼近阈值。你会写出一个正确、在大 batch 时比排序快 3 倍的版本，再从它和 FlashInfer 之间 3–10 倍的差距里看出好算法长什么样。

## 背景

每个 decode step、每个请求都要从 logits 里采样一个 token。采样参数（temperature、top-k、top-p、min-p）各不相同，词表大小 V 约为 3 万到 25 万。教科书做法是先**排序**再求累积和：对 64 个请求、15 万的词表，单是 `torch.sort` 就要约 1 ms，和一整层 decode 的时间相当。

FlashInfer 的采样和 renorm kernel **从不排序**：它反复对“概率大于某个 pivot 的元素”做 (质量, 个数) 的归约，根据结果移动 pivot，直到找到阈值。每一轮都是一次在片上完成的全词表规约，不需要全局排序，也不需要额外的显存。

## 要用到的知识：对浮点位模式二分

- 对非负的 fp32，**把它的位模式当成 int32 解释后，大小顺序与浮点值一致**。所以阈值可以在整数区间 `[0, bits(max) + 1)` 上二分，31 次就能**精确**定位到某一个 fp32 值，不会有浮点二分的精度问题。
- 不变式：`f(lo)` 满足条件，`f(hi)` 不满足：
  - top-k：条件是 `count(x ≥ t) ≥ k`；
  - top-p：条件是 `mass(x ≥ t) ≥ p`。
- 结束时保留 `x ≥ value(lo)` 的元素再归一化。没有并列值时，top-k 正好留下 k 个；top-p 留下的是“按概率从大到小累加，刚好达到 p 的最小集合”（与 FlashInfer 的语义一致，已在 RTX 5090 上验证）。
- Triton：`x.to(tl.int32, bitcast=True)` 按位重新解释；一个 program 负责一行，每一轮都在 `for start in range(0, V, BLOCK)` 循环里扫一遍整行。

## 提示

::: hint 1 三个阶段
1. 扫一遍求行最大值 → `hi = bits(max) + 1`，`lo = 0`。
2. 31 轮二分：每轮扫一遍，统计 `bits(x) ≥ mid` 的个数（top-k）或质量（top-p），据此更新 lo 或 hi。
3. 扫一遍求保留部分的总和，再扫一遍写出归一化后的结果。
:::

::: hint 2 常见坑
- 在浮点值上二分（`mid = (lo + hi) / 2`）：几十次之后才能收敛，而且相邻的两个概率值可能非常接近，导致结果差一个元素。在位模式上二分，31 次就是精确的。
- 用 `>` 而不是 `≥`：不变式和最终的保留条件必须用同一个比较。
- `hi` 初值设为 `bits(max)`：此时 `count(x ≥ hi) ≥ 1`，不满足“hi 不满足条件”的不变式（k = 1 时会出错）。
:::

::: hint 3 二分循环
```python
for _ in range(31):
    mid = lo + (hi - lo) // 2
    acc = tl.zeros([BLOCK], dtype=tl.float32)
    for start in range(0, V, BLOCK):
        x = tl.load(base + start + offs, mask=start + offs < V, other=0.0)
        above = x.to(tl.int32, bitcast=True) >= mid
        acc += above.to(tl.float32) if IS_TOP_K else tl.where(above, x, 0.0)   # 拆成两个 constexpr 分支
    ok = tl.sum(acc, axis=0) >= (k if IS_TOP_K else p)
    lo = tl.where(ok, mid, lo)
    hi = tl.where(ok, hi, mid)
```
:::

## 测完之后

RTX 5090 实测（V = 151936）：

| | B = 1 | B = 64 |
|---|---|---|
| 你的 top-k = 20 | 268 us | 312 us |
| FlashInfer top-k = 20 | **25 us** | **88 us** |
| 你的 top-p = 0.9 | 268 us | 311 us |
| FlashInfer top-p = 0.9 | **76 us** | **164 us** |
| `torch.sort`（只是排序） | 59 us | 1020 us |

（`BLOCK = 4096, num_warps = 16`；最初用 `BLOCK = 1024, num_warps = 4` 时是 887 us，只调这两个参数就快了 3.3 倍。）

**为什么还差 3–10 倍**（B = 1 的 top-k 差距最大）：你的版本固定扫 33 遍整行，而且每行只有一个 program，B 很小时只用到一个 SM；B = 1 时甚至比 `torch.sort` 还慢，B = 64 时才快 3 倍。FlashInfer 的做法：

- **用数据决定 pivot**：从一个采样得到的值或当前的上下界出发，每轮同时检查两个 pivot（源码里的 `pivot_0`、`pivot_1`），通常几轮就能收敛，而不是固定 31 轮；
- 每轮的 `(sum, count)` 用 CUB 的 BlockReduce 完成，每个线程一次读 16 字节；
- top-k 还有专门的基数选择（radix select）实现，并且支持**多个 CTA 协作处理同一行**（`include/flashinfer/topk.cuh` 中的 multi-CTA radix top-k），正好解决 B 很小时只能用一个 SM 的问题。

**对拍时的一个发现**：top-p 在 32 行中有 4 行和 FlashInfer 差一个 token，而这 4 行在边界处累积质量与 p 的差距都在 1e-6 以内。用 float64 排序的 reference 检查，你的结果是对的：FlashInfer 的 fp32 归约顺序在这种边界情况下会多留或少留一个 token。测试因此允许边界处有 ±1 个 token 的差异。真实采样中这无关紧要，但这是 **kernel 对拍时“容差该怎么定”** 的一个好例子。

进阶：

- 让一行由多个 program 协作完成（每个 program 负责一段，每轮做一次跨 program 的归约），解决 B = 1 时只用一个 SM 的问题。
- 读 `include/flashinfer/sampling.cuh` 中的 `TopPRenormProb`（launcher）及其调用的 kernel，以及 `flashinfer/sampling.py` 中 `top_k_top_p_sampling_from_probs` 的 `filter_apply_order` 参数：先 top-k 还是先 top-p，结果为什么会不一样？

::: answer 面试追问：为什么采样不用排序？用了会怎样？
排序是 O(V log V) 的全局操作，需要额外的显存和多次全局读写；而 top-k / top-p 只需要知道一个阈值。不排序的做法是让每一轮都在片上完成一次全词表归约，代价是 O(V × 轮数)，轮数很小，数据还在 L2 里。batch 增大后排序的代价迅速上升（本题 B = 64 时 `torch.sort` 要 1 ms，FlashInfer 的 top-k 只要 88 us）。另外，不排序的实现更容易做到每个请求使用不同的 k / p，并且可以把采样直接融合进同一个 kernel，不必先把过滤后的分布写回显存。
:::
