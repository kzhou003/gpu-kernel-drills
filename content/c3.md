lede: 转置不做任何计算，却能把带宽从 30% 提到 90%：这题专门练合并访存和 shared memory 的 bank conflict。

## 背景

转置本身很常见（layout 转换、`x.t().contiguous()`、attention 里的 K^T、各种 permute），但它真正的价值是**教学**：读和写不可能同时对行主序连续。naive 版本要么读是合并的、写是跨步的，要么反过来。解决办法是用 shared memory 当“中转站”，这和 GEMM、FlashAttention 里 staging tile 的思路完全一样。

## 要用到的知识

- 二维 launch：`dim3 block(32, 8)`，`dim3 grid(ceil(N/32), ceil(M/32))`。
- 约定 `threadIdx.x` 走内存中连续的维度。
- `__shared__ float tile[32][33];` 以及 `__syncthreads()`。
- **bank conflict**：`tile[i][j]` 的地址是 `i·33 + j`，所在 bank 是 `(i·33 + j) % 32`。没有 padding 时是 `(i·32 + j) % 32 = j`：一个 warp 读一列（i 变、j 固定）时，32 个线程全部落在同一个 bank，访问被串行化成 32 次。

## 题目要求

完成 `mine/c3_transpose.cu` 的两个 kernel（host 代码和 launch 配置已给出）：

1. **`transpose_naive_kernel`**：block (32, 8)，一个线程搬一个元素，`y[c][r] = x[r][c]`。
2. **`transpose_tiled_kernel`**：block (32, 8) 负责一个 32×32 的 tile，每个线程搬 4 行。
   - 第 1 步：合并地读 x 的 tile 到 shared memory；
   - `__syncthreads()`；
   - 第 2 步：交换 block 坐标，让 `threadIdx.x` 仍然沿 y 的行方向走，合并地写出。

x 为 `[M, N]` 连续 float32，M、N 任意（包括 1、不是 32 的倍数）。结果必须**逐位相等**。

## 提示

::: hint 1 画出两个坐标系
block `(bx, by)` 负责 x 中行 `by·32 … by·32+31`、列 `bx·32 … bx·32+31` 的 tile。这个 tile 转置后是 y 中行 `bx·32 …`、列 `by·32 …` 的 tile。写回时把 bx 和 by 的角色对调，同时**让 `threadIdx.x` 继续对应输出的列**，这样写也是连续的。
:::

::: hint 2 下标对照
- 读：`c = bx·32 + tx`，`r = by·32 + ty + j`（j = 0, 8, 16, 24），`tile[ty + j][tx] = x[r][c]`。
- 写：`yc = by·32 + tx`（y 的列 = x 的行），`yr = bx·32 + ty + j`（y 的行 = x 的列），`y[yr][yc] = tile[tx][ty + j]`。
- 边界：读时检查 `r < M && c < N`，写时检查 `yr < N && yc < M`。
- 两个阶段之间必须 `__syncthreads()`：第 2 步读的是**别的线程**在第 1 步写进去的数据。
:::

::: hint 3 关键几行
```cpp
for (int j = 0; j < TILE; j += ROWS)
  if (r0 + j < M && c < N) tile[threadIdx.y + j][threadIdx.x] = x[(int64_t)(r0 + j) * N + c];
__syncthreads();
for (int j = 0; j < TILE; j += ROWS)
  if (yr0 + j < N && yc < M) y[(int64_t)(yr0 + j) * M + yc] = tile[threadIdx.x][threadIdx.y + j];
```
其中 `r0 = blockIdx.y*TILE + threadIdx.y`，`yc = blockIdx.y*TILE + threadIdx.x`，`yr0 = blockIdx.x*TILE + threadIdx.y`。
:::

## 测完之后

- RTX 5090 上 8192×8192 的实测：naive 667 us · 805 GB/s，`x.t().contiguous()` 668 us · 804 GB/s（PyTorch 的通用拷贝 kernel 在这里也是跨步写），**tiled 381 us · 1409 GB/s**（峰值的 ~79%）。你在别的 GPU 上的数字会不同，但 tiled 应明显快于另外两个。
- **去掉 padding**（`tile[32][32]`）再测一次，用 `ncu` 的 `l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld` 指标看 bank conflict 的数量。
- 把 block 改成 (32, 32)，每个线程只搬一个元素：线程多了，速度却不一定更快。为什么？（每个线程只做一次 load / store，相对开销更大；block 越大，每个 SM 能同时驻留的 block 也越少。）
- 想一想：GEMM（C4）里 B 的 tile 读进 shared memory 之后，是按行读还是按列读？会不会冲突？

::: answer 面试追问：为什么不直接让每个线程读 x[r][c]、写 y[c][r]？写入不合并到底慢在哪？
一个 warp 的 32 个线程写 y 的同一列（相邻 r），地址相隔 M·4 字节，落在 32 个不同的 32 字节 sector 上。硬件要发 32 个独立的写事务，每个事务只用 4 字节，有效带宽只剩 1/8。shared memory 中转之后，读和写都是 32 个连续 float，各需 4 个 sector。
:::
