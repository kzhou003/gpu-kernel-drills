lede: MoE 层的第一步不是矩阵乘，而是“排队”：给每个 token 选专家，把 (token, 专家) 对按专家分组并补齐到 tile 大小，这样后面一次 launch 就能算完所有专家。

## 背景

MoE（Mixtral、Qwen3-MoE、DeepSeek-V3、gpt-oss、Kimi K2）把 MLP 换成 E 个专家，每个 token 只送到 top-k 个专家（E = 64–256，k = 2–8）。计算上就变成：对每个专家 e，用分到它的那些 token 做一次小 GEMM。

直接写成 `for e in experts: y[idx_e] = x[idx_e] @ W_e` 会启动 E 个 kernel，而且每个都很小。高效的做法是先把 (token, slot) 对**按专家排序**，并把每个专家的那一组**补齐到 BLOCK_M 的整数倍**。这样每个 BLOCK_M 行的块只属于一个专家，一个 grouped GEMM kernel（M2）就能一次算完。vLLM 的 `moe_align_block_size` 做的就是这件事。

## 要用到的知识

- **路由**（Mixtral / Qwen-MoE 风格）：对专家做 softmax，取 top-k，再把这 k 个权重重新归一化。DeepSeek-V3 用 sigmoid 打分加分组限制的路由，原理相同。
- **扁平编号**：`f = t·K + k`（第 t 个 token 的第 k 个槽位）。补齐位置填 `T·K`，这是一个越界的编号，GEMM 会把它屏蔽掉。
- PyTorch：`torch.bincount`（每个专家的 token 数）、`torch.argsort(stable=True)`（稳定排序，保持组内 token 的原始顺序）、`torch.repeat_interleave`。
- 不准写对 token 或专家的 Python 循环：真实系统里这一步在 GPU 上完成，T·K 可以达到几十万。

## 提示

::: hint 1 先算每个专家的组从哪里开始
`counts = bincount(flat)` → `padded = ceil(counts / block_m) · block_m` → `pad_start = cumsum(padded) − padded`（不含自身的前缀和）。P 就是 `padded.sum()`。
:::

::: hint 2 每个元素要去哪
`order = argsort(flat, stable=True)` 给出按专家分组后的扁平编号。它在自己组内的名次 `rank = arange(n) − group_start[expert]`（`group_start` 是未补齐的 counts 的前缀和），目标位置 `dest = pad_start[expert] + rank`。
:::

::: hint 3 收尾
```python
sorted_ids = torch.full((P,), T * K, dtype=torch.int32)
sorted_ids[dest] = order.int()
expert_ids = torch.repeat_interleave(torch.arange(E), padded // block_m).int()
```
:::

## 测完之后

- 补齐带来的浪费：T = 16（decode）、E = 64、k = 8 时，平均每个专家只有 2 个 token，block_m = 64 会让大部分行都是补齐行。这就是为什么 decode 阶段的 MoE kernel 要用更小的 block_m，或者换一种布局（DeepGEMM 的 masked grouped GEMM：为每个专家预留固定的最大行数，配合 CUDA graph 使用）。
- vLLM 的 `moe_align_block_size` 是一个 CUDA kernel（单个 block 内用 shared memory 做计数和前缀和）。用 Triton 或 CUDA 把你的 PyTorch 版本改写成一个 kernel，看看能比这几次 PyTorch 调用快多少。
- **负载不均衡**：热门专家的 token 数可能是平均值的好几倍，grouped GEMM 的时间取决于最慢的那个专家。专家并行（EP）时还有跨卡不均衡的问题，DeepSeek 的 EPLB 通过复制热门专家来缓解。

::: answer 面试追问：为什么要把 token 按专家排序？直接对每个 token 做 gather 不行吗？
GEMM 的效率来自数据复用：同一个专家的权重被多个 token 共用，才能组成矩阵乘、用上 Tensor Core。按专家分组之后，一个块里的所有行都乘以同一块权重，权重只需要读一次。按 token 逐个 gather 权重，就退化成矩阵乘向量，每个 token 都要读一遍 k 个专家的权重，变成严重的 memory-bound。补齐到 block_m 是为了让每个块只对应一个专家，代价是少量补齐行的浪费。
:::
