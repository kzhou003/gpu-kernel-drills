lede: 在 Mac 上写第一个 GPU kernel：MLX 的 mx.fast.metal_kernel 只要你写 Metal kernel 的函数体，其余（签名、编译、缓存、调度）它都替你做。顺便弄清 Metal 和 CUDA 在 grid 语义上的关键差别。

## 背景

MLX 是 Apple 为 Apple silicon 做的数组框架，`mlx-lm`、`mlx-vlm` 等项目在 Mac 上运行 LLM 都靠它。它的 GPU 后端是 Metal：GEMM、attention、量化 matmul、各种融合算子都是 MLX 仓库里手写的 Metal kernel（`mlx/backend/metal/kernels/`）。`mx.fast.metal_kernel` 让你不改 MLX 源码，就在 Python 里写出一个自定义 kernel，和 MLX 的其他操作混合使用，也能被 `mx.compile` 处理。

Apple GPU 的特点：**统一内存**（CPU 和 GPU 共用同一块内存，不需要拷贝），带宽从 M2 的约 100 GB/s 到 Ultra 芯片的约 800 GB/s；没有独立显存，所以“模型能不能放下”取决于整机内存。

## 要用到的知识：CUDA ↔ Metal 对照

| CUDA | Metal / MLX |
|---|---|
| `__global__ void k(...)` | MLX 根据 `input_names`、`output_names` 和函数体中用到的属性**自动生成签名**；你只写函数体 |
| block / thread | threadgroup / thread |
| warp（32） | simdgroup（Apple GPU 上是 32） |
| `blockIdx`、`threadIdx` | `threadgroup_position_in_grid`、`thread_position_in_threadgroup` |
| `blockIdx.x * blockDim.x + threadIdx.x` | `thread_position_in_grid` 直接给出全局编号 |
| `<<<grid（block 数）, block>>>` | `grid=`**线程总数**、`threadgroup=` 每组线程数（Metal 的 dispatchThreads；grid 不需要是 threadgroup 的整数倍） |
| `__shared__` | `threadgroup` 内存 |
| `template <typename T>` | `template=[("T", mx.float16)]`：模板参数在调用时传入 |

- 输入数组变成 `const device T* x`（很小的输入可能被放在 `constant` 地址空间，见 X2），Python 标量变成 `constant int& n` 这样的参数。
- 默认 `ensure_row_contiguous=True`：输入不连续时，MLX 会先复制一份连续的再交给 kernel。
- `header=` 放辅助函数；数学函数在 `metal::` 命名空间下，`metal::precise::tanh` 是精确版本，`metal::fast::` 是快速近似版本。

## 题目要求

在 `mine/x1_metal_elementwise.py` 中补全三段 Metal 源码：

1. `_HEADER`：`inline float gelu_tanh(float z)`。
2. `_SRC`：每个线程处理一个元素，`out[i] = T(gelu_tanh(float(x[i]) + float(y[i])))`。
3. `_SRC_VEC`：每个线程处理 `N_PER` 个连续元素（模板参数）。

要求支持 fp32 / fp16 / bf16、任意形状、转置过的输入。

## 提示

::: hint 1 函数体只有三行
`uint i = thread_position_in_grid.x;`，检查 `i < n`，写回。grid 传的是线程总数 n，所以不用再乘 threadgroup 大小。
:::

::: hint 2 常见坑
- 把 grid 当成 threadgroup 的个数（CUDA 习惯）：会启动 256 倍的线程，越界写坏内存，或者直接报错。
- 用 `half` 做中间计算：`z³` 很快就溢出了。全程用 `float`，存回时转成 `T`。
- 在 `_SRC_VEC` 里忘了对最后一个线程做边界检查。
- 改了 Metal 源码却没有生效：MLX 按 `name` 和源码缓存编译结果，在同一个 Python 进程里重新创建 kernel 时注意 name 的唯一性。
:::

::: hint 3 两段源码
```c++
// _SRC
uint i = thread_position_in_grid.x;
if (i < n) out[i] = T(gelu_tanh(float(x[i]) + float(y[i])));
// _SRC_VEC
uint base = thread_position_in_grid.x * N_PER;
for (uint j = 0; j < N_PER; ++j) { uint i = base + j; if (i < n) out[i] = T(gelu_tanh(float(x[i]) + float(y[i]))); }
```
:::

## 测完之后

Apple M2（24 GB）实测，fp16，n = 2²⁴：MLX 自带操作（`mx.compile` 融合后）2191 us · 46 GB/s，你的单元素版本 2381 us · 42 GB/s，4 元素版本 2365 us · 43 GB/s。

- 先测这台机器实际能达到的带宽：同一时刻 `x + 1`（fp32，2²⁴ 个元素）是 59 GB/s。M2 的标称带宽约 100 GB/s，测试时机器负载较高（load average ≈ 17）。memory-bound kernel 的性能要和**实测的上限**比较，而不是和标称值比较。
- 和 CUDA 一样，elementwise kernel 的速度由带宽决定，你的实现和 MLX 内置操作在同一水平。
- 用 Xcode 的 Metal System Trace（Instruments）或 `mx.metal.start_capture()` 抓一次 GPU trace，看 kernel 的实际时间和占用率。
- MLX 的 `mx.compile` 也能把多个逐元素操作自动融合成一个 kernel。什么时候还需要手写？（当融合需要 threadgroup 内存、跨线程归约或特殊的数据布局时：X2、X3。）

::: answer 面试追问：Apple GPU 和 NVIDIA GPU 写 kernel 时最大的区别是什么？
编程模型很接近（threadgroup ≈ block，simdgroup ≈ warp，threadgroup 内存 ≈ shared memory），主要区别在于：统一内存，没有 host 与 device 之间的拷贝，但带宽比数据中心 GPU 低一个数量级，所以 LLM 推理几乎总是 memory-bound，量化（4-bit / 8-bit 分组量化）是最有效的手段；矩阵单元是 simdgroup 级别的 8×8 `simdgroup_matrix`（M5 起还有 GPU 内的 neural accelerator），而不是 Tensor Core 那样更大的 MMA；工具链是 Metal Shading Language（C++14 方言）和 Xcode / Instruments，而不是 nvcc / Nsight。
:::
