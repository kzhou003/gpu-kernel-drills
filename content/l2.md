lede: decode 阶段每个序列只有 1 个新 query，却要读完它整个历史的 KV：这是一个纯 memory-bound 的问题。GQA 让多个 query head 共用一份 KV，kernel 要利用这一点，把每个 page 只读一次。

## 背景

prefill（T5）是 compute-bound 的：Q 有很多行，`QKᵀ` 是真正的矩阵乘。decode 时每个序列每个 head 只有一个 query 向量：

- 计算量：每个 KV token 约 `4·D` FLOPs（点积 + 加权求和）
- 读取量：每个 KV token 要读 `2·D` 个数（K 和 V）

算术强度约为 1，远低于硬件拐点，**时间 ≈ KV cache 字节数 / 带宽**。所以 decode 优化的核心问题是：**怎样把 KV 读得尽量少、尽量快**。

**GQA**（Grouped-Query Attention，LLaMA-2 70B、LLaMA-3、Qwen 等）：`Hq` 个 query head 共享 `Hkv` 个 KV head，`GROUP = Hq / Hkv`（常见是 4 或 8）。如果每个 query head 各开一个 program，同一份 KV 会被读 GROUP 次；如果一个 program 负责一个 KV head 下的全部 GROUP 个 query head，KV 只读一次，算术强度也随之提高 GROUP 倍。

## 要用到的知识

- 输入：`q [B, Hq, D]`；`k_cache, v_cache [num_blocks, PAGE, Hkv, D]`；`block_tables [B, max_blocks]`；`context_lens [B]`。
- 一个 program = (序列 b, kv head)：`grid = (B, Hkv)`。
- 这个 program 的 query：`q_heads = kvh·GROUP + [0, GROUP)`，组成一个 `[GROUP, D]` 的小矩阵。`tl.dot` 要求 M ≥ 16，所以补到 `GROUP_PAD = max(16, next_pow2(GROUP))` 行，多出的行填 0，最后不存。
- 按 page 循环：`phys = block_tables[b, p]`，读 `[PAGE, D]` 的 K、V。
- `tl.trans(k)`：`[PAGE, D] → [D, PAGE]`，然后 `s = tl.dot(q, tl.trans(k))`，得到 `[GROUP_PAD, PAGE]`。
- 最后一个 page 不满：`tok = p·PAGE + offs_t`，`tok >= ctx` 的位置分数设为 −inf。
- 跨 page 的 softmax：与 T5 完全相同的 online softmax。

## 提示

::: hint 1 和 T5 比，只有三处不同
1. query 不是 `[BLOCK_M, D]` 的连续一块，而是同一个 kv head 下的 GROUP 个 head（补齐到 GROUP_PAD 行）。
2. key 的位置不是 `start_n + arange`，而是先查 block table 找到物理 page，再在 page 内偏移。
3. 每个序列的长度不同：循环上界是 `cdiv(context_lens[b], PAGE)`，最后一个 page 用 mask。
:::

::: hint 2 地址
```text
q:      Q + b·stride_qb + q_heads[:, None]·stride_qh + offs_d[None, :]
k / v:  CACHE + phys·stride_cb + offs_t[:, None]·stride_ct + kvh·stride_ch + offs_d[None, :]
out:    O + b·stride_ob + q_heads[:, None]·stride_oh + offs_d[None, :]   (mask: offs_g < GROUP)
```
`phys` 要转成 int64：`num_blocks · stride_cb` 很容易超过 2³¹。
:::

::: hint 3 循环体
```python
for p in range(0, tl.cdiv(ctx, PAGE)):
    phys = tl.load(block_tables + b * stride_btb + p).to(tl.int64)
    t_mask = (p * PAGE + offs_t) < ctx
    kv_off = phys * stride_cb + offs_t[:, None] * stride_ct + kvh * stride_ch + offs_d[None, :]
    k = tl.load(K_cache + kv_off, mask=t_mask[:, None], other=0.0)
    v = tl.load(V_cache + kv_off, mask=t_mask[:, None], other=0.0)
    s = tl.where(t_mask[None, :], tl.dot(q, tl.trans(k)) * scale, float("-inf"))
    m_new = tl.maximum(m_i, tl.max(s, axis=1))
    p_ = tl.exp(s - m_new[:, None])
    alpha = tl.exp(m_i - m_new)
    l_i = l_i * alpha + tl.sum(p_, axis=1)
    acc = tl.dot(p_.to(v.dtype), v, acc * alpha[:, None])
    m_i = m_new
```
:::

## 测完之后

- 有效带宽 = `2 · B · ctx · Hkv · D · 2 字节 / 时间`。RTX 5090 实测（Hq = 32、Hkv = 8、D = 128、page 16）：

| B · ctx | 时间 | 有效带宽 |
|---|---|---|
| 64 × 1024 | 176 us | **1520 GB/s**（峰值的 85%） |
| 8 × 4096 | 261 us | 514 GB/s |
| 1 × 32768 | 1839 us | **73 GB/s**（峰值的 4%） |

- **B = 1、ctx = 32768** 时非常慢：只有 `B · Hkv = 8` 个 program，5090 的 170 个 SM 里只有 8 个在工作，每个 program 还要串行走 2048 个 page。这正是 L3 要解决的问题。
- 对比“每个 query head 一个 program”的写法（`grid = (B, Hq)`）：KV 读取量变成 GROUP 倍，看看带宽和时间的变化。
- vLLM 的 paged attention v1 正是这个结构（CUDA 手写，每个 warp 负责一部分 token）；v2 加上了分片，FlashInfer 的 `BatchDecodeWithPagedKVCacheWrapper` 则会根据 batch 和长度自动决定是否分片。

::: answer 面试追问：为什么 decode attention 用不满 Tensor Core？GQA 有什么帮助？
每个 head 只有 1 个 query，`q @ kᵀ` 是矩阵乘向量，Tensor Core 需要至少 16 行的矩阵块。把同一 KV head 下的 GROUP 个 query 打包成一个矩阵，可以凑出更多行（GROUP = 8 时补到 16，有效利用率是 50%），更重要的是 KV 只读一次，算术强度提升 GROUP 倍。投机解码的验证阶段每个序列有多个 query，也会利用同样的打包思路。
:::
