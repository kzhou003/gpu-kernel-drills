lede: 第一次用 FlashInfer：把 L 系列的 block table 换成 FlashInfer 的 CSR 分页格式，理解 plan / run 两段式，再拿官方 decode 和你自己的 L2 / L3 比一比。

## 背景

FlashInfer 是 vLLM、SGLang、TensorRT-LLM、MLC 等框架共用的 attention / sampling / GEMM / MoE kernel 库。它的大部分接口都遵循两个约定，这一题先把它们吃透：

1. **分页 KV 用 CSR 格式描述**，不是 vLLM 那种补齐到最长序列的二维 block table。不同序列的 page 数相差很大（1 个对 2000 个）时，CSR 不浪费空间，也不需要关心 max_blocks。
2. **plan / run 分离**：`plan()` 在 CPU 上根据这一批序列的长度做调度，决定要不要 split-KV、分几段、每个 CTA 处理哪些 page，然后把结果拷到 GPU 的 workspace 里；`run()` 只负责启动 kernel。一个 batch 的形状确定后，plan 只做一次，所有层的 `run()` 都复用它，而且 `run()` 可以被 CUDA graph 捕获。

## 要用到的知识

```text
indptr        [B + 1] int32   序列 b 的 page 是 indices[indptr[b] : indptr[b+1]]
indices       [nnz]   int32   各序列的物理 page 号，按序列依次拼接
last_page_len [B]     int32   每个序列最后一个 page 用了几个 token，取值 1 … page_size
context_len[b] = (indptr[b+1] − indptr[b] − 1) · page_size + last_page_len[b]
```

- 布尔索引 `block_tables[mask]` 按行主序取元素，正好保持“每个序列的 page 连续且有序”。
- 本仓库的 cache 形状 `[num_pages, page_size, H_kv, D]` 就是 FlashInfer 的 **NHD** 布局（另一种是 HND：`[num_pages, H_kv, page_size, D]`）。把 `(k_cache, v_cache)` 作为一个 tuple 传给 `run()`。
- `run(..., return_lse=True)` 会同时返回 LSE。**FlashInfer 的 LSE 以 2 为底**：`lse = log₂ Σ exp(score)`，等于自然对数 LSE ÷ ln 2。F2 要用到这一点。

## 题目要求

在 `mine/f1_flashinfer_paged.py` 中实现：

1. `block_table_to_csr(block_tables, context_lens, page_size) -> (indptr, indices, last_page_len)`：向量化，不准对序列写 Python 循环；全部是 int32。
2. `csr_to_block_table(indptr, indices, last_page_len, page_size) -> (block_tables, context_lens)`：它的逆变换，block table 用 0 补齐。

## 提示

::: hint 1 先算 num_pages
`num_pages = ceil(ctx / page_size)`，`indptr` 是它的前缀和（前面补一个 0），`last_page_len = ctx − (num_pages − 1)·page_size`。indices 就是 block table 中每行前 `num_pages[b]` 个元素拼起来。
:::

::: hint 2 FlashInfer 调用顺序
```python
ws = torch.empty(128 << 20, dtype=torch.uint8, device=q.device)       # workspace
w = flashinfer.BatchDecodeWithPagedKVCacheWrapper(ws, kv_layout="NHD")
w.plan(indptr, indices, last, num_qo_heads, num_kv_heads, head_dim, page_size,
       q_data_type=q.dtype, kv_data_type=k_cache.dtype)
out = w.run(q, (k_cache, v_cache))
```
workspace 用来存放 split-KV 的中间结果。第一次调用会 JIT 编译对应 dtype / head_dim 的 kernel，需要几十秒。
:::

::: hint 3 两个转换函数
```python
keep = torch.arange(max_blocks)[None, :] < num_pages[:, None]
indices = block_tables[keep].int()              # 行主序 = 每个序列依次排列
# 逆变换
block_tables = torch.zeros(B, max_blocks, dtype=torch.int32); block_tables[keep] = indices
```
:::

## 测完之后

RTX 5090 实测（Hq = 32、Hkv = 8、D = 128、page 16，fp16）：

| B × ctx | 你的 L2（不分片） | 你的 L3（最佳分片） | FlashInfer `run()` |
|---|---|---|---|
| 1 × 32768 | 1844 us | 96 us（64 片） | **98 us** |
| 8 × 4096 | 260 us | 95 us（16 片） | **98 us** |
| 64 × 1024 | **174 us** | 176 us（不分） | 180 us |

- FlashInfer 在每种形状下都**自动**选到了接近最优的分片方式：这正是 `plan()` 的工作。你的 L3 需要手动为每种形状挑选 `num_splits`。
- 把 `plan()` 也计入时间试试：它在 CPU 上运行并要同步，所以真实系统里每个 batch 只调用一次，再被所有层复用。
- 读源码：`flashinfer/decode.py` 里的 `BatchDecodeWithPagedKVCacheWrapper.plan` → `csrc/batch_decode.cu` → `include/flashinfer/attention/scheduler.cuh`（决定分片的启发式）。把它的分片规则和你在 L3 里观察到的最优分片对照一下。
- `use_tensor_cores=True`：GQA 的 group 较大时，用 prefill kernel 走 Tensor Core 来做 decode。试试对比 group = 8 时的性能。

::: answer 面试追问：为什么 FlashInfer 要把 plan 和 run 分开？
调度决策（分几片、每个 CTA 处理哪些 page、中间结果放在 workspace 的哪里）只取决于这一批序列的长度，对所有层都一样。放在 `plan()` 里在 CPU 上算一次，`run()` 就只剩启动 kernel，形状固定、没有 CPU 同步，可以被 CUDA graph 捕获，每层只付一次 launch 的代价。如果每次调用都现场决定，要么每层都在 CPU 上重复计算，要么只能在 GPU 上用一个保守的固定策略。
:::
