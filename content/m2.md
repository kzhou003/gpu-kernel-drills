lede: 在 T4 的 GEMM 上加两处改动，就得到 vLLM 默认的 MoE kernel：A 的行通过 sorted_token_ids 间接读取，B 的权重块由这一块所属的专家决定。再用它拼出完整的 SwiGLU MoE 层。

## 背景

vLLM 的 `fused_moe` 是一个 Triton kernel，它在大多数 GPU 上都是 MoE 的通用默认实现（Hopper / Blackwell 上还有 DeepGEMM、CUTLASS、TRT-LLM 等更专门的后端）。它的结构和 T4 几乎一样，只多了两处间接寻址：

1. 这个 program 负责的 BLOCK_M 行不是连续的行，而是 `sorted_token_ids[块]` 指向的 (token, slot) 对。第一个 GEMM 里，多个 slot 共用同一个 token 的输入行（`token = f // K`）。
2. B 是 `W[expert_ids[块]]`：同一个块里所有行属于同一个专家（M1 保证了这一点）。

## 要用到的知识

- 完整的 MoE MLP（SwiGLU）：

```text
w13 [E, 2I, H]：每个专家的 gate 和 up 投影拼在一起；w2 [E, H, I]：down 投影
h  = x[t] @ w13[e]^T          -> [2I]       第一个 grouped GEMM（A 行 = token）
h  = silu(h[:I]) · h[I:]      -> [I]        F3 的 silu_and_mul
y  = h @ w2[e]^T · weight     -> [H]        第二个 grouped GEMM（A 行 = (token, slot)，乘上路由权重）
out[t] = Σ_k y[t, k]                         把 k 个专家的结果加起来
```

- 地址：`a_ptrs = a + a_rows[:, None] · stride_am + offs_k[None, :]`，其中 a_rows 是 gather 来的行号；W[e] 是 `[N, Kdim]` 的行主序矩阵，加载它的转置块 `[BLOCK_K, BLOCK_N]`：`w + e·stride_we + offs_n[None, :]·stride_wn + offs_k[:, None]`。
- 行 mask：`flat_ids < num_valid`（补齐行不读不写）。
- 在 epilogue 里把路由权重乘进去（`MUL_WEIGHT`），省掉一次单独的逐元素 kernel。

## 题目要求

`fused_moe_gemm` 的 wrapper 和 `moe_layer` 已写好。实现 `fused_moe_kernel`：

- grid = (补齐后的块数, cdiv(N, BLOCK_N))。
- `A_ROWS_ARE_TOKENS`（constexpr）：True 时 A 的行号是 `flat_id // top_k`，False 时就是 `flat_id`。

## 提示

::: hint 1 和 T4 只差在开头
T4 里的 `offs_m` 直接就是行号；这里先 `flat_ids = load(sorted_ids + offs_m)`，再由 flat_ids 推出 A 的行号和输出的行号。专家号是一个标量：`expert = load(expert_ids + pid_m)`。
:::

::: hint 2 常见坑
- 补齐行的 flat_id 等于 T·K，`T·K // top_k = T` 也越界：A 的加载一定要带上 row_mask。
- 输出要写到 `out[flat_id]`，而不是 `out[offs_m]`：后者是排序后的位置，结果的顺序会全部打乱。
- 第二个 GEMM 的 A 是中间结果 h，它的行本身就是 `[T·K, I]`，不能再除以 top_k。
- 64 位地址：`expert · stride_we` 和 `a_rows · stride_am` 都可能超过 2³¹，先转成 int64。
:::

::: hint 3 kernel 主体
```python
offs_m = pid_m * BLOCK_M + tl.arange(0, BLOCK_M)
flat_ids = tl.load(sorted_ids_ptr + offs_m)
row_mask = flat_ids < num_valid
expert = tl.load(expert_ids_ptr + pid_m).to(tl.int64)
a_rows = flat_ids // top_k if A_ROWS_ARE_TOKENS else flat_ids          # 写成 constexpr if
a_ptrs = a_ptr + a_rows[:, None].to(tl.int64) * stride_am + offs_k[None, :]
w_ptrs = w_ptr + expert * stride_we + offs_n[None, :] * stride_wn + offs_k[:, None]
# ... 与 T4 相同的 K 循环 ...
if MUL_WEIGHT:
    acc = acc * tl.load(topk_w_ptr + flat_ids, mask=row_mask, other=0.0)[:, None]
tl.store(out_ptr + flat_ids[:, None].to(tl.int64) * stride_om + offs_n[None, :], acc.to(...), mask=...)
```
:::

## 测完之后

RTX 5090 实测：T = 4096、E = 64、top-8、H = 2048、I = 768（接近 Qwen3-30B-A3B 的专家形状），bf16：

| | 时间 | TFLOP/s |
|---|---|---|
| 你的 MoE 层（两次 grouped GEMM，block 64×64×32） | 3245 us | 95 |
| 同等 FLOPs 的两次稠密 cuBLAS GEMM | 1461 us | 212 |

- 差距的来源：固定的 64×64×32 tile 没有针对这个形状调优；补齐行带来的浪费；gather 读取 A 不如连续读取高效；silu_and_mul 和最后的求和是单独的 PyTorch 操作。vLLM 为每种 (E, N, K, GPU) 组合准备了调好的 JSON 配置文件，加上 autotune 往往就能拿回一大部分性能。用 T4 的 autotune 试试。
- 融合：把 silu_and_mul 放进第一个 GEMM 的 epilogue（每个 program 同时计算 gate 和 up 两个 N 块），省掉一次中间结果的写回和读取。
- 和 FlashInfer 对比：`flashinfer.cutlass_fused_moe`、`flashinfer.fused_moe` 等 API 提供了 CUTLASS / TRT-LLM 后端的 MoE，读一读它们的接口，看看都融合了哪些步骤（路由、排列、两次 GEMM、激活、合并）。

::: answer 面试追问：MoE 在 decode 和 prefill 时的瓶颈有什么不同？
prefill 时 token 多，每个专家能分到足够多的行，grouped GEMM 是 compute-bound 的，优化重点是 tile 配置、负载均衡和 FP8 / FP4 量化。decode 时 token 很少，每个专家只有几行，GEMM 退化成读一遍被激活专家的权重，是 memory-bound 的；而且一个 batch 激活的专家数可能接近全部专家，读的权重比稠密模型还多。这时的优化手段是更小的 block_m、权重量化（每读一个字节就算得更多）、配合 CUDA graph 的 masked 布局，以及专家并行时的通信与计算重叠。
:::
