## 背景

C4 用 CUDA 手写了 tiling 和 register tiling，但没有用 Tensor Core。Triton 把 C4 的一整套（shared memory staging、寄存器分块、Tensor Core 指令、软件流水线）都交给编译器，你只需要描述 **“一个 program 算 C 的哪一块、沿 K 怎么走”**。官方 Matrix Multiplication tutorial 就是这道题的原型。真实系统里，vLLM 的 MoE `fused_moe` kernel、各种量化 GEMM 也都是在这个骨架上改出来的。

## 要用到的知识

- **二维指针块**：`a_ptrs = a_ptr + offs_m[:, None] * stride_am + offs_k[None, :] * stride_ak`，得到 `[BLOCK_M, BLOCK_K]` 的指针。用 stride 而不是假设行主序，所以转置后的输入（stride (1, M)）也能用。
- **`tl.dot(a, b, acc)`**：`acc += a @ b`。a、b 是 fp16 / bf16，acc 是 fp32。三个维度都至少 16。
- **沿 K 循环**：`for k in range(0, tl.cdiv(K, BLOCK_K))`，每轮 `a_ptrs += BLOCK_K * stride_ak`。最后一段 K 不满时用 mask 填 0。
- **grouped ordering**：把一维的 `pid` 映射成 `(pid_m, pid_n)` 时，不按行主序排，而是把 `GROUP_M` 行 tile 编成一组，在组内先沿列方向（m 方向）走。
- **autotune**：`triton.autotune(configs=[...], key=["M", "N", "K"])`。

## grouped ordering 是什么

C 被切成 `num_pid_m × num_pid_n` 个 tile。同一时刻 GPU 上同时在跑的 program 大约有 SM 数 × 每 SM 驻留数这么多。如果按行主序编号，同时在跑的是一整行 tile：它们共用 A 的同一个行条带，却各需要 B 的一个不同列条带，B 的工作集很大，L2 装不下。分组之后，同时在跑的是 `GROUP_M` 行 × 若干列的一块方形区域：A 和 B 的条带都被多个 program 复用。

```text
pid 的编号顺序（num_pid_m = 4, num_pid_n = 3）

行主序：          GROUP_M = 2：
 0  1  2           0  2  4
 3  4  5           1  3  5
 6  7  8           6  8 10
 9 10 11           7  9 11
```

```python
num_pid_in_group = GROUP_M * num_pid_n
group_id = pid // num_pid_in_group
first_pid_m = group_id * GROUP_M
group_size_m = min(num_pid_m - first_pid_m, GROUP_M)      # 最后一组可能不满
pid_m = first_pid_m + ((pid % num_pid_in_group) % group_size_m)
pid_n = (pid % num_pid_in_group) // group_size_m
```

## 提示

::: hint 1 四段式
1. pid → (pid_m, pid_n)（上面的公式）
2. 造 `a_ptrs`、`b_ptrs`，`acc = tl.zeros((BLOCK_M, BLOCK_N), tl.float32)`
3. K 循环：masked load → `acc = tl.dot(a, b, acc)` → 指针前进
4. `acc.to(c 的类型)`，按 `(offs_m < M) & (offs_n < N)` 做 masked store
:::

::: hint 2 常见坑
- K 方向的 mask：用 `k_remaining = K - k * BLOCK_K` 和 `offs_k < k_remaining`，而不是 `offs_k < K`（offs_k 每轮都是 0…BLOCK_K−1）。
- 只对 a 的 m 方向和 b 的 n 方向做 mask，忘了 K 方向：最后一段会读到下一行的数据，结果错得不明显。
- 指针前进写成 `a_ptrs += BLOCK_K`：输入转置后 stride_ak 不是 1。
- `tl.dot` 的输入如果被提前转成 fp32，就用不上 fp16 Tensor Core 了（在 Ampere 上会走 TF32，慢很多，精度也不同）。
:::

::: hint 3 主循环
```python
acc = tl.zeros((BLOCK_M, BLOCK_N), dtype=tl.float32)
for k in range(0, tl.cdiv(K, BLOCK_K)):
    k_remaining = K - k * BLOCK_K
    a = tl.load(a_ptrs, mask=(offs_m[:, None] < M) & (offs_k[None, :] < k_remaining), other=0.0)
    b = tl.load(b_ptrs, mask=(offs_k[:, None] < k_remaining) & (offs_n[None, :] < N), other=0.0)
    acc = tl.dot(a, b, acc)
    a_ptrs += BLOCK_K * stride_ak
    b_ptrs += BLOCK_K * stride_bk
```
:::

## 测完之后

- RTX 5090 实测（fp16，单位 TFLOP/s）：512³ 时 21.7 vs cuBLAS 26.8（81%）；1024³ 115.5 vs 116.9；2048³ 164.4 vs 164.6；4096³ 209.3 vs 211.0；8192³ **217.8 vs 217.7**。从 1024 开始基本追平 cuBLAS。小矩阵时 tile 数不够填满 170 个 SM，差距更大。
- 把 `GROUP_M` 改成 1（退化为行主序），在 8192³ 上对比：L2 命中率（`ncu` 的 `lts__t_sector_hit_rate`）和时间都会变差。
- 记录 autotune 为每个 shape 选中的 config（`matmul_kernel_autotuned.best_config`），观察大 shape 和小 shape 的选择有什么不同。这正是原计划 Week 4 要求的实验记录。
- `num_stages` 从 2 调到 5：stage 越多预取越深，但每个 stage 都要占一份 shared memory，超过上限会编译失败或降低 occupancy。
- 进阶：在 epilogue 里融合 bias + 激活（`c = gelu(acc + bias)`），这是 GEMM 融合最常见的形式。

::: answer 面试追问：Triton GEMM 和 cuBLAS 差在哪里？
大 shape 下主要差在一些底层细节：Hopper 上的 TMA 和 wgmma 异步流水线、warp specialization（一部分 warp 只负责搬数据，一部分只负责算）、persistent kernel（program 数等于 SM 数，循环处理多个 tile），以及为特定 shape 手工调过的 tile 配置。新版 Triton 和 Gluon 已经能显式表达其中大部分优化；小 shape 下差距主要来自启动开销和 SM 利用率（split-K、stream-K 能缓解）。
:::
