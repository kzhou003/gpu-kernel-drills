lede: vLLM 每一步 forward 的第一个自定义 kernel：把新 token 的 K、V 按 block table 写进分页的 KV cache。先用纯 PyTorch 算出 slot，再用 Triton 搬数据。

## 背景

**PagedAttention** 把 KV cache 切成固定大小的 block（page，通常 16 个 token），像操作系统的虚拟内存一样按需分配：每个序列有一张 **block table**，记录它的第 i 个逻辑 block 存在哪个物理 block。这样可以消除碎片，还能让多个序列共享前缀 block。

每一步 forward，新算出的 K、V（prefill 时是整段 prompt，decode 时每个序列一个 token）都要先写进 cache。调度器会为每个 token 预先算好一个 **slot**：

```text
slot = block_table[seq][pos // block_size] * block_size + pos % block_size
```

cache 布局为 `[num_blocks, block_size, H_kv, D]`，并且是连续的，所以 slot s 的数据就在扁平偏移 `s · H_kv · D` 处。vLLM 里对应的是 `reshape_and_cache` / `reshape_and_cache_flash`（CUDA），以及 `slot_mapping` 的计算。

## 要用到的知识

- PyTorch 的高级索引：`block_table[seq_idx, logical_block]` 一次性 gather 出 T 个物理 block 号。
- 每个 token 一个 program；token 的 `H·D` 个值当作一维向量搬运（`BLOCK = next_power_of_2(H·D)`）。
- **padding token**：slot = −1 表示跳过（CUDA graph 的 batch 被补齐时会出现）。用 mask 让整个 program 什么都不写。
- key / value 可能是 fused qkv 投影结果的 view：行 stride 是 `3·H·D` 而不是 `H·D`，但每行内部的 `[H, D]` 是连续的。

## 提示

::: hint 1 slot_mapping 三行
`logical = positions // block_size` → `physical = block_table[seq_idx, logical]` → `physical * block_size + positions % block_size`。记得都转成 `long`。
:::

::: hint 2 kernel
- `t = tl.program_id(0)`，`slot = tl.load(slot_ptr + t)`。
- 源地址：`key_ptr + t * key_stride + offs`；目标地址：`k_cache_ptr + slot * HD + offs`。
- 跳过 padding：最直观的写法是 `mask = (offs < HD) & (slot >= 0)`。它在 GPU 上没问题，但 CPU 解释器不接受由标量和块组合出来的 mask。可以换一种等价写法：`n_valid = tl.where(slot >= 0, HD, 0)`，`mask = offs < n_valid`。
:::

::: hint 3 kernel 全文
```python
t = tl.program_id(0).to(tl.int64)
slot = tl.load(slot_ptr + t)
offs = tl.arange(0, BLOCK)
mask = offs < tl.where(slot >= 0, HD, 0)
k = tl.load(key_ptr + t * key_stride + offs, mask=mask)
v = tl.load(value_ptr + t * value_stride + offs, mask=mask)
tl.store(k_cache_ptr + slot * HD + offs, k, mask=mask)
tl.store(v_cache_ptr + slot * HD + offs, v, mask=mask)
```
:::

## 测完之后

- 这是纯拷贝 kernel：有效带宽按“读 key + value、写两个 cache”计算。RTX 5090 实测：T = 8192、H = 8、D = 128 时 53.5 us · **1254 GB/s**（slot 是随机排列的，写入比顺序拷贝分散一些）。
- **FP8 KV cache**：在写入时量化（`cache = (k / scale).to(fp8)`），cache 容量翻倍，decode 读 KV 的字节数减半。改写 kernel 加一个 per-tensor 的 scale。
- vLLM 的 CUDA 版本区分了两种 cache layout：`[num_blocks, block_size, H, D]`（flash 布局，本题用的）和把 D 再切成 `x = 16 字节` 小块的旧布局（为 paged attention v1/v2 的向量化读取设计）。读源码时留意 `reshape_and_cache` 和 `reshape_and_cache_flash` 的区别。
- 为什么 block_size 一般是 16？太小：block table 变长，attention kernel 的间接寻址更多；太大：内部碎片（最后一个 block 的浪费）变多，前缀共享的粒度也更粗。

::: answer 面试追问：paged KV cache 相比连续 KV cache 的代价是什么？
attention kernel 每读一个 page 都要先查 block table，多一次间接寻址；物理上不连续，也不能用一次大的连续拷贝。好处是几乎没有碎片、可以动态增长、可以在序列之间共享前缀 block（copy-on-write），并发量因此能提高好几倍。page 大小是这两者之间的权衡。
:::
