lede: 每个 decoder layer 都要做两次“残差加 + RMSNorm”和一次 SwiGLU：按 FlashInfer 的语义（包括原地写回两个张量）用 Triton 实现它们，并和官方 kernel 比带宽。

## 背景

pre-norm Transformer 的每一层：

```text
h = x + attn(rmsnorm(x));   x = h + mlp(rmsnorm(h))
```

serving 框架会把“残差加”和“下一个 RMSNorm”融合成一个 kernel：`fused_add_rmsnorm(x, residual, w)`。它读 x 和 residual 各一次，然后**原地**写回两个张量：residual 更新为 `x + residual`，作为残差流继续往下传；x 更新为归一化后的结果，作为下一个子层的输入。MLP 里的 SwiGLU 同样融合成一个 kernel：`silu_and_mul(gate_up) = silu(gate) · up`。

这两个 kernel 都在 FlashInfer 的 `flashinfer/norm` 和 `flashinfer/activation.py` 里。它们是 FlashInfer 中最简单的一类实现，也是 F5 推荐的第一条源码阅读路线。

## 要用到的知识

- **原地语义**：函数返回 None，测试会检查两个张量的 data_ptr 没有变。wrapper 里要用 `view` 而不是 `reshape`：张量不连续时 `reshape` 会悄悄拷贝一份，写回就丢了。
- **精度约定**（和 FlashInfer 一致）：`h = x + residual` 在 fp32 里计算；存回 residual 时转成 residual 的 dtype；归一化使用 fp32 的 h。
- `silu(g) = g · sigmoid(g)`；输入 `[..., 2d]` 的前一半是 gate，后一半是 up（这个顺序已在 FlashInfer 上验证过）。
- silu_and_mul 用二维 grid：`(行数, cdiv(d, BLOCK))`。d 很大（比如 14336）时，一个 program 只处理一段，program 数也更多。

## 题目要求

wrapper 已写好。实现 `fused_add_rmsnorm_kernel` 和 `silu_and_mul_kernel`：

- fp32 / fp16 / bf16；N 任意（≤ 16384）。
- GPU 上与 `flashinfer.fused_add_rmsnorm`、`flashinfer.silu_and_mul` 对拍（bf16，H = 4096、I = 11008）。

## 提示

::: hint 1 fused_add_rmsnorm 的顺序
load x、r（fp32）→ `h = x + r` → **先**把 h 存进 residual → 用 h 算 rstd → 存 `h·rstd·w` 进 x。两个 store 写的是不同的张量，先后顺序不影响正确性；但都要发生在 load 之后。
:::

::: hint 2 常见坑
- 用 T3 的 `rms_norm` 再加一次残差加：结果对，但多读写了一遍，就失去了融合的意义。
- wrapper 里写成 `x.reshape(-1, N)`：非连续输入时写回不到原张量。
- silu_and_mul 把前后两半弄反：FlashInfer 是 `silu(前一半) · 后一半`。
:::

::: hint 3 kernel 主体
```python
x = tl.load(x_ptr + row * x_stride + cols, mask=mask, other=0.0).to(tl.float32)
r = tl.load(r_ptr + row * r_stride + cols, mask=mask, other=0.0).to(tl.float32)
h = x + r
tl.store(r_ptr + row * r_stride + cols, h.to(r_ptr.dtype.element_ty), mask=mask)
rstd = 1.0 / tl.sqrt(tl.sum(h * h, axis=0) / N + eps)
w = tl.load(w_ptr + cols, mask=mask, other=0.0).to(tl.float32)
tl.store(x_ptr + row * x_stride + cols, (h * rstd * w).to(x_ptr.dtype.element_ty), mask=mask)
```
:::

## 测完之后

RTX 5090 实测（bf16）：

| 算子 | T = 16（decode） | T = 4096（prefill） |
|---|---|---|
| fused_add_rmsnorm，H = 4096 | 你的 6.2 us / FlashInfer 6.2 us | 你的 **88 us · 1522 GB/s** / FlashInfer 90 us |
| silu_and_mul，I = 14336 | 你的 **6.1 us** / FlashInfer 8.2 us | 你的 244 us / FlashInfer 242 us |

- 大 T 时两者都到了带宽上限：这类 memory-bound 的 kernel，Triton 写起来容易，性能也够好。
- 小 T 时时间都在 6 us 左右：这是 launch 和调度的下限。decode 阶段这类 kernel 的优化方向是进一步**融合**（和前后的 GEMM、量化合并）以及 **PDL**（Programmatic Dependent Launch，Hopper 起支持，允许下一个 kernel 提前启动）。FlashInfer 的 API 带 `enable_pdl` 参数，RMSNorm 源码中的 `griddepcontrol` 指令就是它。
- 读源码：`flashinfer/norm/__init__.py` 的 `rmsnorm` → `flashinfer/jit/norm.py`（`gen_norm_module`）→ `csrc/norm.cu` 和 `csrc/flashinfer_norm_binding.cu` → `include/flashinfer/norm.cuh` 里的 `RMSNorm` / `FusedAddRMSNorm`。关注 `vec_size = gcd(16 / sizeof(T), d)` 和 `block_size = min(1024, d / vec_size)` 这两行：它是怎么决定向量化宽度和线程数的？
- 进阶：FlashInfer 有 `fused_add_rmsnorm_quant`、`fused_add_rmsnorm_fp8_block_quant`，把 FP8 量化也并进来。结合 M3，自己实现一个“残差加 + RMSNorm + 1×128 FP8 量化”的融合 kernel。

::: answer 面试追问：为什么这些小算子在 decode 时值得花力气优化？
decode 时每层的 GEMM 也很小（矩阵乘向量），一层 attention + MLP 的总耗时可能只有几十微秒，而每个小算子都有几微秒的固定开销。一个 decoder layer 里有 RMSNorm × 2、残差加 × 2、RoPE、SwiGLU、量化等十来个小算子，不融合时它们的开销加起来可以和 GEMM 相当。所以 decode 优化的重点是减少 kernel 数量（融合、CUDA graph、PDL），而不是把单个小 kernel 再提速 10%。
:::
