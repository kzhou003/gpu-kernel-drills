lede: 第一个 CUDA kernel：把线程编号算对、把 launch 配置配对，再体会“融合”为什么能直接省一半时间。

## 背景

逐元素运算（加法、激活函数、bias、残差、类型转换）在 Transformer 里无处不在。它们的算术强度极低（vector add 每 12 字节才 1 次加法），**速度完全由搬了多少字节决定**。

PyTorch 里写 `F.gelu(x + bias)` 会启动两个 kernel：第一个读 x、写临时张量 t；第二个读 t、写 y，一共 4 趟显存读写。把它们写进一个 kernel（**fusion**），只要读 x、写 y 两趟，理论上快一倍，也少一次 launch。`torch.compile`、TensorRT、vLLM 的自定义算子做的大部分工作就是这类融合。

## 要用到的知识

- 全局线程编号：`int64_t i = (int64_t)blockIdx.x * blockDim.x + threadIdx.x;`
- launch 配置：`blocks = ceil(n / threads)`，即 `(n + threads - 1) / threads`。
- **边界检查**：最后一个 block 通常不满，`if (i < n)` 必不可少。
- **grid-stride loop**：`for (i = 起点; i < total; i += blockDim.x * gridDim.x)`，grid 大小可以与数据量无关。
- `tanhf`：CUDA 数学库的单精度 tanh。
- 行主序 `[rows, cols]` 中，扁平下标 i 对应的列号是 `i % cols`。

## 题目要求

在 `mine/c1_elementwise.cu` 里完成：

1. **`vector_add_kernel`**：`c[i] = a[i] + b[i]`，每个线程处理一个元素；以及 host 函数里的 `blocks` 计算。
2. **`gelu_tanh`**：`0.5·x·(1 + tanh(√(2/π)·(x + 0.044715·x³)))`，与 `F.gelu(approximate="tanh")` 一致。
3. **`bias_gelu_kernel`**：`y[r][c] = gelu_tanh(x[r][c] + bias[c])`，用 grid-stride loop；host 里 `blocks = min(ceil(total/threads), SM 数 × 32)`。

输入都是连续的 float32 CUDA 张量；空张量、n = 1、n 不是 256 倍数的情况都要正确。

## 提示

::: hint 1 先写对，再关心性能
- 每个线程只做一件事：算出自己的 `i`，越界就什么都不做。
- `blocks` 是向上取整的除法；n 恰好是 256 的倍数时不能多出一个空 block，不是倍数时不能少一个。
- `bias_gelu` 的 grid 被截断到 `sms * 32`，所以线程必须**循环**：每次跳过整个 grid 的线程数。
:::

::: hint 2 常见坑
- `blockIdx.x * blockDim.x` 在 32-bit 下计算，n 超过 2³² 会溢出：先转 `int64_t`。
- grid-stride 的步长是 `blockDim.x * gridDim.x`（整个 grid 的线程数），不是 `blockDim.x`。
- `x * x * x` 比 `powf(x, 3)` 更快也更准。
- 忘记 `C10_CUDA_KERNEL_LAUNCH_CHECK()` 时，`blocks = 0` 这种错误配置会被静默吞掉，直到后面某个不相干的地方才报错。
:::

::: hint 3 核心几行
```cpp
// vector_add_kernel
int64_t i = (int64_t)blockIdx.x * blockDim.x + threadIdx.x;
if (i < n) c[i] = a[i] + b[i];
// host
const int64_t blocks = (n + threads - 1) / threads;

// bias_gelu_kernel
const int64_t stride = (int64_t)blockDim.x * gridDim.x;
for (int64_t i = (int64_t)blockIdx.x * blockDim.x + threadIdx.x; i < total; i += stride)
    y[i] = gelu_tanh(x[i] + bias[i % cols]);
```
:::

## 测完之后

参考解在 RTX 5090（峰值 ~1.79 TB/s）上的实测：

| 测试 | PyTorch | 参考解 |
|---|---|---|
| vector_add，n = 2²⁰ | 10.2 us · 1229 GB/s | 10.2 us · 1229 GB/s |
| vector_add，n = 2²⁷ | 1028 us · 1567 GB/s | 1027 us · 1568 GB/s（峰值的 ~87%） |
| bias_gelu 8192×8192 | 706 us（两个 kernel） | **379 us**（融合，快 1.86 倍） |

- **算有效带宽**：vector_add 每个元素读 8 字节、写 4 字节。大 n 时和 PyTorch 完全一样：两边都已经被显存带宽卡住了，这正是“memory-bound kernel 的上限就是带宽”。
- **n 再小一些**（比如 2¹⁶）时，时间会停在几微秒不再下降：这是 launch 开销，说明此时测的不是 kernel 本身。
- **融合的收益**：字节数减半，时间也接近减半。
- 试一试：threads 改成 32、64、128、512、1024，带宽有什么变化？为什么 32 明显更慢？（提示：每个 SM 同时驻留的 block 数有上限，block 太小时驻留的 warp 不够，无法隐藏访存延迟。）
- 进阶：用 `float4` 一次读 16 字节（要求 n 是 4 的倍数且地址 16 字节对齐），看看带宽能不能再涨一点。

::: answer 面试追问：为什么 elementwise kernel 的性能和 block 大小关系不大，却对融合非常敏感？
elementwise 的算术强度极低，时间 ≈ 读写字节数 / 带宽。block 大小只要能让 SM 上驻留足够多的 warp 来隐藏延迟（通常 128–512 都可以），带宽就能跑满，再调也没有收益。融合直接减少了必须搬运的字节数和 kernel 数，相当于改变了分子，所以收益是成比例的。
:::
