lede: FlashInfer 的 cascade / split-KV / 前缀共享都建立在同一个原语上：两段 attention 状态 (v, lse) 的精确合并。用 Triton 实现它，并和 flashinfer.merge_state 逐数值对拍。

## 背景

L3 里你已经写过一次合并：多个 split 的部分结果用 LSE 加权求和。FlashInfer 把它做成了独立的公开 API，因为它在很多地方都会用到：

- **split-KV decode**：各分片的结果合并（L3）。
- **cascade / 共享前缀 attention**：一批请求共用一个很长的系统 prompt 时，对共享前缀只做一次 attention（batch 内的所有 query 一起读一份 KV），对各自的后缀单独做，最后把两部分合并（`MultiLevelCascadeAttentionWrapper`）。
- **chunked prefill、ring / context parallel**：分块或分卡算出的部分 attention 结果，都要这样合并。

## 要用到的知识：以 2 为底的 LSE

FlashInfer 的 kernel 内部用 `exp2` 和 `log2`（硬件上有对应的快速指令），所以对外暴露的 LSE 也是以 2 为底：

```text
s = log₂ Σ_j exp(score_j)            (自然对数版 = s · ln 2)
合并 (v_a, s_a) 和 (v_b, s_b)：
  m = max(s_a, s_b),  w_a = 2^(s_a − m),  w_b = 2^(s_b − m)
  v = (w_a v_a + w_b v_b) / (w_a + w_b),  s = m + log₂(w_a + w_b)
```

`2^(s_a − m) = exp((s_a − m)·ln 2)`，就是这一段在总分母中的相对权重；底数只要前后一致就行。**混用底数是常见 bug**：L3 的 LSE 是自然对数，直接拿去和 FlashInfer 的 LSE 合并会得到错误的权重。

形状与 FlashInfer 一致：

| 函数 | 输入 | 输出 |
|---|---|---|
| `merge_state` | `v_a, v_b [S, H, D]`，`s_a, s_b [S, H]` fp32 | `v [S, H, D]`，`s [S, H]` |
| `merge_states` | `v [S, N, H, D]`，`s [S, N, H]` | `v [S, H, D]`，`s [S, H]` |

## 提示

::: hint 1 地址
`v_a` 连续存放、形状 `[S, H, D]`，所以 (位置, head) 的线性编号 `pid = pos·H + h` 对应的向量从 `pid·D` 开始，标量 LSE 在 `pid`。merge_states 中 `s[pos, n, h]` 的位置是 `(pos·N + n)·H + h`。
:::

::: hint 2 一定用 exp2 / log2
`tl.exp2(s − m)` 和 `tl.log2(w_a + w_b)`。用 `tl.exp` 不会报错，但数值会和 FlashInfer 对不上（相当于把以 2 为底的 LSE 当成了自然对数）。
:::

::: hint 3 merge_states 的核心
```python
s = tl.load(s_ptr + (pos * N + offs_n) * H + h, mask=n_mask, other=float("-inf"))
m = tl.max(s, axis=0)
w = tl.exp2(s - m)                                      # 补齐的状态权重为 0
v = tl.load(v_ptr + ((pos * N + offs_n[:, None]) * H + h) * D + offs_d[None, :], mask=..., other=0.0)
out = tl.sum(w[:, None] * v, axis=0) / tl.sum(w, axis=0)
s_out = m + tl.log2(tl.sum(w, axis=0))
```
:::

## 测完之后

- RTX 5090 实测（H = 32、D = 128，fp16）：S = 128 时你的实现和 FlashInfer 都是 6.2 us（纯 launch 开销）；S = 8192 时你的 156 us · 1293 GB/s，FlashInfer 135 us · 1490 GB/s。差距来自向量化宽度和每个 program 的工作量：试试每个 program 处理多个 head。
- 读源码：`flashinfer/cascade.py` 的 `merge_state` → `include/flashinfer/attention/cascade.cuh`。注意它用 `vec_t` 一次读 16 字节，每个线程处理多个元素。
- 用 `MultiLevelCascadeAttentionWrapper` 做一个实验：64 个请求共享一个 8K token 的前缀，比较“cascade”与“每个请求各自读一遍前缀”的耗时，体会共享前缀省下了多少 KV 读取。

::: answer 面试追问：cascade attention 为什么能加速共享前缀？
不用 cascade 时，batch 里每个请求都要从 HBM 读一遍完整的前缀 KV，读取量是 B × 前缀长度。cascade 先把所有请求的 query 一起对共享前缀做一次 attention：前缀的 KV 只读一次，而且多个 query 共用同一块 KV，可以组成矩阵乘、用上 Tensor Core。各请求的后缀再单独计算，最后用 merge_state 合并。合并本身只读写 O(B·H·D) 的数据，相对前缀的 KV 读取可以忽略。
:::
