lede: batch 小、上下文长时，L2 只能启动个位数的 program，GPU 大部分时间在空转。把每个序列的上下文再切成 NUM_SPLITS 段并行算，最后用 log-sum-exp 精确合并：这就是 Flash-Decoding。

## 背景

L2 的 program 数 = `B · Hkv`。B = 1、Hkv = 8 时只有 8 个 program，而 H100 有 132 个 SM。每个 program 还要串行走完 32K 个 token：带宽利用率可能只有 10%。

**Flash-Decoding / split-KV**：沿上下文维度再切一刀。

- **第一步**（`grid = (B, Hkv, NUM_SPLITS)`）：每个 program 只处理自己那一段 page，得到这一段内归一化好的输出 `o_s`，以及这一段的 **log-sum-exp** `lse_s = m_s + log(l_s)`。
- **第二步**（`grid = (B, Hq)`）：合并。

```text
M   = max_s lse_s
w_s = exp(lse_s − M)
out = Σ_s w_s · o_s / Σ_s w_s
```

为什么这样合并是精确的：`lse_s = log Σ_{j∈s} exp(score_j)` 正是这一段的 softmax 分母取对数，所以 `exp(lse_s)` 就是这一段在整体分母中所占的权重。减去 M 只是为了防止溢出，和 T2 中减去 max 的原理相同。

这个合并操作在很多地方都会出现：FlashInfer 的 `merge_state`、vLLM 的 `merge_attn_states`（前缀缓存 / cascade attention 中，把对共享前缀和私有后缀分别做的 attention 合并起来）、ring attention 等。

## 要用到的知识

- 每个 split 负责的 page 范围：`pages_per_split = cdiv(num_pages, NUM_SPLITS)`，`[split·pps, min((split+1)·pps, num_pages))`。
- **空分片**：短序列的后几个 split 可能分不到任何 page。此时 `l = 0`、`m = −inf`，必须写出 `o = 0`、`lse = −inf`，合并时权重为 `exp(−inf) = 0`。不能做 `0/0`，也不能做 `log(0)` 再相加。
- 中间结果用 fp32 存储：`o_part [B, Hq, NUM_SPLITS, D]`，`lse [B, Hq, NUM_SPLITS]`。
- 合并 kernel 一次读入所有分片：`SPLIT_PAD = next_pow2(NUM_SPLITS)`，多出的分片 `lse` 填 −inf。

```python
M = lse.max(-1, keepdim=True)                     # [B, Hq, 1]
w = torch.exp(lse - M)                            # [B, Hq, S]
out = (w[..., None] * o_part).sum(-2) / w.sum(-1, keepdim=True)
```
然后把 L2 的 kernel 复制过来，改循环范围和结尾部分。

::: hint 2 空分片的处理
```python
has = l_i > 0
o   = acc / tl.where(has, l_i, 1.0)[:, None]                          # 空分片：0 / 1 = 0
lse = tl.where(has, m_i + tl.log(tl.where(has, l_i, 1.0)), float("-inf"))
```
`range(p_start, p_end)` 在 `p_start >= p_end` 时一次也不执行，所以 `m_i`、`l_i`、`acc` 保持初始值。
:::

::: hint 3 merge kernel
```python
lse = tl.load(LSE + b * stride_lb + h * stride_lh + offs_s, mask=s_mask, other=float("-inf"))
w = tl.exp(lse - tl.max(lse, axis=0))
o = tl.load(O_part + b * stride_pb + h * stride_ph + offs_s[:, None] * stride_ps + offs_d[None, :],
            mask=s_mask[:, None], other=0.0)
out = tl.sum(w[:, None] * o, axis=0) / tl.sum(w, axis=0)
```

## 测完之后

RTX 5090 实测（Hq = 32、Hkv = 8、D = 128，单位 us，括号内为有效带宽 GB/s）：

| B × ctx | L2（不分片） | splits = 4 | splits = 16 | splits = 64 |
|---|---|---|---|---|
| 1 × 32768 | 1838（73） | 492（273） | 155（865） | **96（1394）** |
| 8 × 4096 | 261（514） | 103（1309） | **95（1420）** | 107（1257） |
| 64 × 1024 | **176（1521）** | 186（1440） | 204（1315） | 262（1024） |

- **B = 1、ctx = 32K**：分 64 片后快了 **19 倍**，带宽从峰值的 4% 升到 78%。
- **B = 64、ctx = 1K**：分片反而更慢：program 数本来就够多，额外的中间结果写回和第二个 kernel 都是纯开销。
- 每一行的最佳分片数都不一样，最优点大约在 `B · Hkv · splits` 达到 SM 数的几倍时。
- 所以真实系统会**根据 B、ctx、SM 数来决定 NUM_SPLITS**：目标是 `B · Hkv · NUM_SPLITS` 大约是 SM 数的若干倍，并且每个分片至少有若干个 page。FlashInfer decode 的 `plan()` 阶段做的就是这件事（它还能让不同长度的序列分到不同数量的分片）。
- 把 merge 融合进第一个 kernel：最后完成的那个分片负责合并（需要一个原子计数器）。省掉一次 launch，代价是实现更复杂。

::: answer 面试追问：只给你每个分片的输出 o_s，不给 lse，能合并吗？
不能。合并需要知道每个分片的 softmax 分母（`exp(lse_s)`）在整体中所占的比例。只有 o_s 时，分片之间的相对权重已经丢失了：两个分片的 o_s 完全相同，背后的分母可能差几个数量级。所以凡是需要“分段计算 attention 再合并”的场景（split-KV、cascade、ring attention、chunked prefill 的跨 chunk 合并），中间结果都要同时保存 o 和 lse（或者等价地保存 m 和 l）。
:::
