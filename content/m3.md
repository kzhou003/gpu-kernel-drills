lede: DeepSeek-V3 的 FP8 配方：激活每 1×128 一个缩放系数，权重每 128×128 一个，每个 K 块做一次 FP8 Tensor Core 矩阵乘再乘上缩放。在 RTX 5090 上，这样写出的 Triton kernel 比 bf16 cuBLAS 快 1.7 倍。

## 背景

FP8（e4m3：最大值 448，只有 3 位尾数）让 Tensor Core 的吞吐翻倍、权重的字节数减半。难点在于动态范围：用一个 per-tensor 的缩放系数，激活里的离群值会把大部分数压成 0。DeepSeek-V3 的做法是**细粒度缩放**：

- 激活：每个 token 的每 128 个通道一个 scale（per-token-group，1×128）；
- 权重：每 128×128 的块一个 scale（per-block）。

每个 128 宽的 K 块恰好对应一组 scale，所以 kernel 可以每算完一个 K 块就乘上这一块的 `sa · sb`，全程保持 fp32 累加。DeepGEMM（SM90 / SM100）就是这个配方的高度优化实现；vLLM 的 `w8a8_block_fp8_matmul` 是它的 Triton 版本。Blackwell 的 MXFP8 / NVFP4 把“块缩放”做进了硬件指令（1×32 或 1×16 一个 scale），思路相同。

## 要用到的知识

- 量化：`scale = max(|x_group|) / 448`，`q = clamp(x / scale, −448, 448).to(fp8)`；scale 存为 fp32。全零的组要用一个很小的 eps，避免除以 0。
- `torch.float8_e4m3fn`；Triton 里 `tl.dot(a_fp8, b_fp8)` 直接得到 fp32 结果（需要 sm_89+）。
- block-scaled GEMM 的主循环：

```text
for kb in K 块（BLOCK_K = 128）：
    acc += tl.dot(A_q[m, kb], B_q[n, kb]^T) · sa[m, kb] · sb[n // 128, kb]
```

  BLOCK_N 取 128 的约数时，一个 tile 里所有列共享同一个 `sb`（一个标量）；`sa` 是 BLOCK_M 个值组成的向量。
- 布局：A `[M, K]`，B `[N, K]`（即 `C = A @ B^T`，和 `nn.Linear` 的权重布局相同）。

e w -> wq

e wq -> dot

::: callout analogy 每 128 个数一把尺子
FP8 只有 3 位尾数，像一把刻度很粗的尺子。用一把尺子（per-tensor scale）同时量蚂蚁和大象，蚂蚁全变成 0；给每 128 个数各配一把合适量程的尺子（block scale），大数小数都量得准。
尺子的切换正好落在每个 K 块的边界上，所以 kernel 每算完一块乘一次 scale 就行，几乎没有额外开销。
:::

## 提示

::: hint 1 量化 kernel 只有几行
加载 128 个值 → `amax = max(max(|x|), eps)` → `scale = amax / 448` → 存 `clamp(x / scale)` 和 scale。scale 的位置是 `row · cdiv(K, 128) + g`。
:::

::: hint 2 GEMM 的两个 scale
- `sa = load(sa_ptr + offs_m · stride_sam + kb)`：形状 `[BLOCK_M]`。
- `sb = load(sb_ptr + ((pid_n · BLOCK_N) // 128) · stride_sbn + kb)`：一个标量。
- `acc += tl.dot(a, b) * (sa[:, None] * sb)`：先把 FP8 的点积在 fp32 里算完，再乘 scale。不能把 scale 乘进 FP8 的输入里（那样就失去了量化的意义），也不要只在最后乘一次（每个 K 块的 scale 不同）。
:::

::: hint 3 主循环
```python
for kb in range(0, tl.cdiv(K, BLOCK_K)):
    k_left = K - kb * BLOCK_K
    a = tl.load(a_ptrs, mask=m_mask[:, None] & (offs_k[None, :] < k_left), other=0.0)
    b = tl.load(b_ptrs, mask=(offs_k[:, None] < k_left) & n_mask[None, :], other=0.0)
    sa = tl.load(sa_ptr + offs_m * stride_sam + kb, mask=m_mask, other=0.0)
    sb = tl.load(sb_ptr + sb_row * stride_sbn + kb)
    acc += tl.dot(a, b) * (sa[:, None] * sb)
    a_ptrs += BLOCK_K
    b_ptrs += BLOCK_K
```
:::

## 测完之后

RTX 5090 实测（单位 TFLOP/s）：

| M × N × K | bf16 cuBLAS | 你的 FP8 block-scaled | 激活量化本身 |
|---|---|---|---|
| 128 × 7168 × 2048 | 108 | **151** | 6 us |
| 4096 × 7168 × 2048 | 219 | **364** | 35 us |
| 4096 × 4096 × 7168 | 218 | **372** | 112 us |

- 大约是 bf16 的 1.7 倍；FP8 在 5090 上的理论峰值约是 bf16 的 2 倍，剩下的差距来自每个 K 块的缩放乘法和流水线深度。
- **激活量化不是免费的**：4096×7168 时要 112 us，占 GEMM 时间的 17%。所以实际系统会把它融合进前一个算子：FlashInfer 的 `fused_add_rmsnorm_fp8_block_quant` 就是“残差加 + RMSNorm + 1×128 FP8 量化”一次完成。把你的 F3 和 M3 合并，实现这个融合算子。
- 在 H100 上，DeepGEMM 用 wgmma + TMA + warp specialization 把同样的计算做到接近 FP8 峰值；它也提供 grouped 版本（contiguous / masked 布局），供 MoE 使用（M1、M2）。
- 进阶：把 M2 的 grouped GEMM 改成 FP8 block-scaled 版本，即 DeepSeek-V3 MoE 的推理配置。

::: answer 面试追问：为什么 DeepSeek-V3 选 1×128 和 128×128 这样的粒度？
粒度越细，离群值的影响范围越小，精度越好；但每个 scale 都要存储、加载，还要在主循环里做一次乘法。128 正好等于一个 K 块，所以 kernel 每个 K 块只需要乘一次 scale，几乎没有额外开销。激活的离群值通常集中在少数通道上，per-token × 每 128 个通道一组可以把它们隔离开；权重的分布比较平滑，128×128 的块就够了，还能让一个 tile 内所有输出列共享同一个 scale。硬件层面，Blackwell 的 MXFP8（每 32 个元素）和 NVFP4（每 16 个元素）把更细的块缩放做进了 MMA 指令。
:::
