lede: 把一百万个数加成一个数：每一层（线程、warp、block、grid）用这一层最便宜的通信手段。softmax、LayerNorm、attention 里的 max 和 sum 都是这个结构。

## 背景

reduction 是很多 kernel 的骨架：softmax 要 max 和 sum，LayerNorm 要 mean 和 var，attention 每行都在做 max / sum，loss 要对整个 batch 求和。难点在于 GPU 上成千上万个线程要把结果**汇合到一个地方**，而不同层级之间的通信代价差了几个数量级：

| 层级 | 通信手段 | 代价 |
|---|---|---|
| 线程内 | 寄存器累加 | 几乎免费 |
| warp 内 | `__shfl_down_sync` 直接交换寄存器 | 每轮几个周期，无需同步 |
| block 内 | shared memory + `__syncthreads()` | 需要一次 barrier |
| block 之间 | global memory 的 `atomicAdd`，或第二个 kernel | 最贵 |

好的 reduction 尽量在便宜的层级做完，只把极少量数据交给更贵的层级。

## 要用到的知识

- `__shfl_down_sync(0xffffffff, v, offset)`：读取 `lane + offset` 号 lane 的 v。offset 依次取 16、8、4、2、1，5 轮之后 lane 0 持有整个 warp 的和。
- `lane = threadIdx.x & 31`，`warp = threadIdx.x >> 5`。
- `__shared__ float warp_sums[WARPS];`：每个 warp 一个槽位。
- `__syncthreads()`：所有 warp 写完自己的槽位之后，warp 0 才能去读。
- `atomicAdd(out, v)`：每个 block 只做一次。
- 模板参数 `template <int BLOCK>`：让 block 大小成为编译期常量，shared memory 数组的大小才能用它。

## 题目要求

完成 `mine/c2_reduce_sum.cu` 中的 `warp_reduce_sum` 和 `reduce_sum_kernel<BLOCK>`：

- 输入 float32 一维连续张量 x，输出 0 维张量 `x.sum()`；host 端已经把 out 初始化为 0。
- grid 被截断为 `min(ceil(n/BLOCK), SM 数 × 4)`，所以每个线程必须用 grid-stride loop 累加多个元素。
- 每个 block 恰好执行**一次** `atomicAdd`。
- 精度：与 float64 reference 的相对误差在 `1e-4` 以内（测试用 `[0, 1)` 均匀分布）。

## 提示

::: hint 1 四层结构
1. 线程：`float v = 0; for (grid-stride) v += x[i];`
2. warp：`v = warp_reduce_sum(v);`，之后只有 lane 0 的值有意义。
3. block：lane 0 写 `warp_sums[warp]`，`__syncthreads()`，然后让 warp 0 的前 `WARPS` 个 lane 读回来，再做一次 `warp_reduce_sum`。
4. grid：warp 0 的 lane 0 做 `atomicAdd(out, v)`。
:::

::: hint 2 常见坑
- `__syncthreads()` 不能放在 `if (lane == 0)` 里面：所有线程都必须执行到它。
- 第二轮 warp 归约时，`lane >= WARPS` 的 lane 要贡献 0，不能读 `warp_sums` 越界。
- `__shfl_down_sync` 的掩码必须包含所有调用它的 lane。在 `if (warp == 0)` 里面整个 warp 0 都进入了，所以用 `0xffffffff` 是对的。
- 测试反复跑结果末位会变：这是浮点原子加的顺序不确定，不是 bug。
:::

::: hint 3 核心代码
```cpp
for (int offset = 16; offset > 0; offset >>= 1) v += __shfl_down_sync(0xffffffff, v, offset);

// kernel 里
const int lane = threadIdx.x & 31, warp = threadIdx.x >> 5;
if (lane == 0) warp_sums[warp] = v;
__syncthreads();
if (warp == 0) {
  v = (lane < WARPS) ? warp_sums[lane] : 0.0f;
  v = warp_reduce_sum(v);
  if (lane == 0) atomicAdd(out, v);
}
```
:::

## 测完之后

- n = 2²⁶ 时应接近峰值带宽：只读 4n 字节，最终只有几百次 atomic。RTX 5090 实测：参考解 176 us · **1524 GB/s**，`torch.sum` 198 us · 1358 GB/s；n = 2²⁰ 时两者都只有 ~10 us，此时主要是 launch 开销。
- **对比实验**：把 warp shuffle 换成教科书式的 shared memory 树形归约（`for (s = BLOCK/2; s > 0; s >>= 1) { if (tid < s) sm[tid] += sm[tid + s]; __syncthreads(); }`），用 `ncu` 比较 barrier 次数和时间。
- **确定性**：如果要求每次结果逐位一致（比如训练的可复现性），把 atomic 换成两趟：第一个 kernel 把每个 block 的部分和写进数组，第二个 kernel 用一个 block 按固定顺序归约它们。
- Triton 里这一整套只是一行 `tl.sum(x, axis=0)`：T2、T3 会用到。G1 会解释编译器怎么把它拆成线程内累加、shuffle 和 shared memory 这三层。

::: answer 面试追问：为什么 grid 只开 SM 数 × 4 个 block，而不是 n / 256 个？
每个 block 最后都要做一次 atomicAdd，block 越多，同一地址上排队的原子操作越多；而只要每个 SM 上有几个 block 在跑，带宽就已经跑满了。让每个线程用 grid-stride loop 多累加几个元素，大部分归约都留在寄存器里完成，最便宜。
:::
