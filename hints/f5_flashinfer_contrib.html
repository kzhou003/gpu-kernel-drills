① 先看全貌：一个 API 的五层

拿 flashinfer.rmsnorm(x, w) 举例，一次调用依次经过：

层 文件 这一层的源码 职责
① flashinfer/norm/__init__.py flashinfer@flashinfer_api + def rmsnorm → flashinferget_norm_module().rmsnorm(…) 检查形状、分配输出、决定走哪个后端
② 同上 flashinfer@functools.cache def get_norm_module 进程内只编译 / 加载一次
③ flashinfer/jit/norm.py flashinfergen_norm_module：两个源文件 + -DENABLE_BF16 -DENABLE_FP8 描述“要编译什么”，返回 JitSpec
④ csrc/norm.cu + 绑定 flashinfervoid rmsnorm(TensorView …)，flashinfer按 dtype 分发并调用 norm::RMSNorm；导出 flashinferTVM_FFI_DLL_EXPORT_TYPED_FUNC(rmsnorm, …) 把框架的张量换成裸指针，选模板实例
⑤ include/flashinfer/norm.cuh launcher flashinferRMSNorm（算 vec_size 和 block_size），kernel flashinferRMSNormKernel 真正的 CUDA kernel

这条链和你在本套题里写的东西一一对应：第 ⑤ 层就是 T3 / F3 的 kernel，第 ④ 层相当于 C1 里的 host 函数 vector_add，第 ① 层相当于每道题 .py 文件里的 Python 包装函数。

类比 · 电器和插头转换器

include 里的 kernel 是一台只认“裸电压”（裸指针）的电器，它不关心电是从哪个国家的插座来的（PyTorch、JAX 还是别的框架）。csrc 里的 launcher 和 TVM-FFI 绑定是插头转换器：把 PyTorch 张量这种“国标插头”转换成电器要的裸电压。所以项目有一条硬规定：include 里不能 include Torch 的头文件。电器里不能焊死某一国的插头，否则换个国家就用不了。

② 为什么要这样分层

框架无关：项目的 CLAUDE.md 写明“Torch headers MUST NOT be included in include/ directory files”。kernel 只收裸指针和整数，同一份 kernel 可以被不同框架复用。

TVM-FFI：绑定层用的不是 pybind11，而是 Apache TVM 的 FFI。TensorView 是一个与框架无关的张量视图（基于 DLPack），TVM_FFI_DLL_EXPORT_TYPED_FUNC 把 C++ 函数导出成可以从 Python 直接调用的符号。你在 C1 里用的 torch/extension.h + TORCH_CHECK 是 PyTorch 专用的做法；FlashInfer 的 flashinferTVM_FFI_ICHECK_EQ 是它的对应物。

JIT：kernel 的模板参数组合太多（dtype × head_dim × 架构 × 各种开关），全部预编译不现实，所以用到哪个组合才编译哪个。

变量 作用

类比 · 打印店的底版

打印店（JIT）收到一份订单（API 调用 + 参数），先查有没有现成的底版（缓存键匹配的 .so）。底版的编号里记着原稿的指纹（源码哈希）：原稿改了一个字，指纹就变了，旧底版作废，重新制版。所以你只管改原稿，不用操心去通知打印店。

④ 第一个 PR：拆成可执行的步骤

题目页 Lab 4 列了几个方向。不管选哪个，流程是一样的：

一个最小的例子：给 rmsnorm 补一个边界测试（hidden size 不是 8 的倍数，这时 vec_size = gcd(8, d) 会退到更小的值）。

git checkout -b test-rmsnorm-odd-hidden
# 1. 在 tests/norm/ 里找到 rmsnorm 的参数化测试，加上 hidden_size = 1004（gcd(8, 1004) = 4）之类的值
pytest tests/norm -k "rmsnorm and not cake" -x -q
# 2. 在你的 GPU 上全部通过，再跑格式检查
pre-commit run -a
git commit -am "test(norm): cover rmsnorm hidden sizes not divisible by 8"
git push -u origin test-rmsnorm-odd-hidden
# 3. 开 PR，用默认模板；CI 里评论：@flashinfer-bot run tests/norm/

PR 模板逐节填写

项目的 flashinferPR 模板：

小节 写什么
flashinferDescription 改了什么、为什么。squash merge 之后这段就是 commit message，几个月后有人 git bisect 到这里，读的就是它
flashinferRelated Issues 对应的 issue 编号
flashinferChecklist · Pre-commit 确认装了并运行过 pre-commit
flashinferTests 加了哪些测试；是否需要全量 CI（默认不需要，需要的话要说明理由）
flashinferExperimental Track 如果改动在 flashinfer/experimental/ 下，填 tracking issue
flashinferReviewer Notes 希望 reviewer 重点看什么；性能 PR 的 benchmark 表格放这里

性能 PR 的数字怎么给：GPU 型号、问题规模、改动前后的绝对时间（不只是加速比）、用的哪个 benchmark 命令。例如：

RTX 5090, bf16, T=4096, H=4096, benchmarks/flashinfer_benchmark.py --routine <对应的 routine> ...
before: 92.1 us   after: 88.3 us
类比 · 病历要写给下一个医生看

PR 描述不是写给现在的 reviewer 看的，而是写给半年后排查回归的人看的：他从 git log 里找到这个 commit，手里只有这段描述。“优化了 norm”是一句没用的病历；“RTX 5090 上 hidden=4096 时 rmsnorm 从 92 us 降到 88 us，原因是改用 16 字节向量化读取”才能让下一个医生对症下药。

⑤ 读源码时的几个入口

  • 项目给新人的三个参考实现（由易到难）：flashinfernorm/init.py（不用 Jinja）、flashinfersampling.py（用了 Jinja 模板）、flashinferdecode.py（plan / run 和 workspace，F1 讲过）。
  • 你在本套题里接触过的 FlashInfer 代码：F1 的 flashinferdecode 调度、F2 的 flashinferMergeStateKernel、F3 的 flashinferFusedAddRMSNormKernel、F4 的 flashinferTopPRenormProbKernel、T1 的 flashinferTriton silu_and_mul。从熟悉的算子开始读，最容易看出门道。
  • API 日志装饰器：flashinferflashinfer_api；实验性 API：flashinferflashinfer_experimental_api。

⑥ 常见坑与自查

  • pip install -e . 没加 --no-build-isolation：pip 可能另装一个 CUDA 版本不同的 torch，后面全乱。
  • clone 没加 --recursive：3rdparty/cutlass 是空的，编译报找不到头文件。补救：git submodule update --init --recursive。
  • 在 include 里 #include <torch/...>：违反分层规则，review 一定会被打回。
  • CI 评论不带路径：@flashinfer-bot run 不带路径会跑全部测试，代价很高。
  • 自己发明 PR 描述格式：项目明确要求保留默认模板。
自测：改了 include/flashinfer/norm.cuh 里的一行，需要重新 pip install 吗？为什么？

不需要。JIT 的缓存键包含源文件的 SHA256，下次调用 rmsnorm 时 FlashInfer 发现哈希变了，会自动重新生成源码、重新编译。前提是用 pip install -e .（可编辑安装），这样 Python 包里的 data/include 是指向你仓库目录的符号链接。
